# 読みやすく分かりやすい文章を書く

**担う**: 読者の特定、目的の設定、文意の決定、構造の設計、文の組み立て、段階ごとの評価。

**担わない**: 素材にない事実・数値・主張を作ること。内容は呼び出し側の文脈から来る。

## 原則: 上から作り、上から直す

**一度に全文を書かない。** 上の層が決まってから下の層に進む。評価で落ちたら、落ちた層まで戻る。

層は五つ。**読者と目的 → 文意 → 構造 → 節 → 文**。

作る順がこうなのは、階層アウトラインを作ってから書いた文章が最も質が高いという実験結果による
（Kellogg）。直す順がこうなのは、熟達した書き手が推敲で議論の形そのものを見直すのに対し、
未熟な書き手は語の入れ替えに終始するという観察による（Sommers）。
**下の層をいくら直しても、上の層が間違っていれば直らない。**

段階は行き来してよい。書いている途中で文意が変わることは普通に起きる。そのときは下の層を直さず、
変わった層まで戻ってから下へ降りる。

慣れた型の短い文章では、段階4 と段階5 を頭の中で済ませてよい。

---

## 段階1: 読者層を決める

読み手は個人とは限らない。チーム・部門・全社・不特定多数も読者層であり、
**個人は「一人しかいない読者層」として同じ形式で扱う。**

プロファイルは `audiences/<id>.md` にある。無ければ素材から作り、同じ場所に保存してから使う。
特定できないときは `audiences/general.md` を使う。**必ずどれか 1 つに着地させる。**

| 読者層 | 素材元 |
|---|---|
| 社内メンバー個人 | `people/members/<name>/`（1on1 の蓄積、特に「最近の傾向」） |
| 発信者自身 | `profile/` |
| 社内の集団 | `organizations/`、そのチャンネルの過去ログ、定例の議事録 |
| それ以外 | 過去のやり取り（Slack・議事録・PR コメント） |

項目は七つ。役割と責務、前提知識、関心、読む量の予算、既存の立場、関係、読み方の好み。
埋まらない項目は空のままにし、推定で埋めない。

**集団は分布を持つので、潰し方を固定する。**

1. 前提知識と読む量の予算は、**最も条件の厳しい層に合わせる**。平均ではなく下限
2. 立場が割れている論点は「割れている」と書き、一つに丸めない

**読み手が複数層にまたがるときは、質問せず構造で解く。** 決裁者と実装者の両方が読む文書に
「どちらですか」と聞いても答えは出ない。層ごとに区画を分け、どこまで読めばよいかを本文に書く。

**外部の個人**はコードネームで管理し、氏名・連絡先をファイルに書かない。

**更新**: 推定が外れたら、プロファイルの「推定が外れた記録」に一行追記してから終わる。

### 人間に質問してよいこと

次の三つが読み取れないときだけ質問する。それ以外は推定し、推定内容を出力に添えて訂正できる形にする。

1. 読み手が決裁者か実行者か
2. この文章の目的（段階2 の分類のどれか）
3. 社内向けか社外向けか

## 段階2: 目的を決める

**読み終えた読者がどうなっているかを一文で書く。** これが以降の全判断の基準になる。

```
悪い例: 新しい skill について説明する
良い例: 読み終えた読者が、この skill を自分で試すか見送るかを判断できている
```

目的の種類で、後の構造が決まる。

| 種類 | 読み終えた読者の状態 | 必要な要素 |
|---|---|---|
| **行動を促す**（依頼・相談・提案） | 何をすればよいか分かっている | してほしいこと・期限・判断材料・断る場合の選択肢 |
| **判断を共有する**（決定・報告） | 何が決まったか・なぜかを説明できる | 決めたこと・理由・却下案とその理由・影響範囲 |
| **理解させる**（説明・解説・記事） | 対象を自分の言葉で説明できる | 中心となる考え・支える根拠・具体例・限界 |
| **記録する**（議事・ログ・手順） | 後から探して同じ結論に到達できる | 事実・日付・決定と保留・参照先 |

複数にまたがるなら、**主たる目的を一つ選ぶ**。副次的な目的は本文の外（付録・リンク）へ出す。

## 段階3: 既知と未知を仕分ける

読者層の前提知識を使って、素材を三つに分ける。**この仕分けが分量を決める。**

- **既知**: 読者が既に知っている。説明せず、文脈の足がかりとして使う
- **知るべき未知**: 目的の達成に必要。本文に置く
- **知らなくてよい**: 目的の達成に不要。**落とす**

落とす対象は、書き手には重要に見えて読者の判断を変えないもの。典型はこう書かれている。

```
落とす: 「調べたところ、A 案と B 案が見つかりました。A 案は〇〇のため見送り、B 案を採りました」
残す:  「B 案で進めます」（判断の共有が目的なら A 案の却下理由まで残す）

落とす: 「Bransford & Johnson (1972) の実験では、題を読む前に与えた群だけ理解が向上しました」
残す:  「最初の一文に用件を書いてください」
```

**根拠を本文に書かない。** 裏付けは書き手が持つもので、読者が判断に使わないなら出さない。
専門外の読者に論文名を渡すと、負荷が増えるだけで納得は増えない。読者が検証を求める立場に
いるときだけ、参照先を末尾かリンクに置く。

**明示の度合いは前提知識で変える。** 接続関係を明示して丁寧に橋渡しした文章は前提知識の低い
読者を助けるが、前提知識の高い読者では明示しすぎるとかえって理解が下がることがある。
**既定は「迷ったら明示する」**とし、前提知識が高いと分かっている層に限って橋渡しを減らす。

## 段階4: 文意を一文で書く

**この文章が言いたいことを一文で書く。** 書けないなら、まだ書き始める段階にない。

一文にまとめた中心の主張を「中心文」と呼ぶ。支える主張は**三つまで**。四つ以上出てきたら、
そのうちのいくつかは中心文の言い換えか、別の文章にすべき内容である。

```
中心文: 文章の伝達の失敗は、書き手に見えにくいだけで原因はほぼ決まっている
支える主張1: 相手に何をしてほしいか書いていない
支える主張2: 期限が相対表現のまま残っている
支える主張3: 背景と依頼が一文に混ざっている
```

中心文は本文のどこかにそのまま置く。多くの場合は冒頭。

## 段階5: 構造を作る

**見出しレベルまでの階層アウトラインを作る。** ここが質を最も左右する。思いつきを並べるだけでは
効果がなく、階層にして初めて効く。

1. **分量の予算を決める**。読者層の「読む量の予算」から、節の数と節あたりの長さを逆算する。
   予算が小さいなら、支える主張を三つから二つに減らす。**構造を削るのであって、文を削らない**
2. **枠を先頭に置く**（下記）
3. **中心文を冒頭に置く**。経緯・背景・検討過程は後ろに回す
4. **見出しを並べ、見出しだけ読んで筋が通るか確かめる**。通らないなら順序か粒度が間違っている

### 枠の置き方

読み手が本文を読み始める前に、これが何の文章かを渡す。**読む前に与えたときだけ効果があり、
読んだ後に与えても効果がない**ことが実験で確かめられている。末尾に「というわけで承認をお願い
します」と書く構成は、そこに至るまで読み手が何を判断しながら読めばよいか分からない状態を作る。

| 媒体 | 枠の形 |
|---|---|
| Slack | 角括弧ラベル＋一文（`【相談】料金改定について、今週中に意見をください。`） |
| 文書 | 表題の直下に一文（`この文書は〇〇の設計方針を決めるためのものです。`） |
| メール | 件名＋冒頭一文 |

**説明や解説が目的の文章では、ラベルを付けない。** 表題と冒頭の一文で対象と範囲が分かれば足りる
（`Kotlin の coroutine のキャンセル処理について、実装で踏みやすい落とし穴を書きます。`）。
種類のラベルが要るのは、読者に行動や判断が求められる文章に限る。

### 見出し・箇条書き・強調

構造を目に見える形にすると読み手は話題の切れ目を掴めるが、副作用がある。

- **見出し**: 話題が三つ以上あるときに付ける。見出しがあると**思い出せる話題の数は増えるが、
  各話題について思い出せる中身は減る**。拾い読みしてほしい文書には効き、一つのことを深く
  理解してほしい文書では効かない。見出しは内容を特定できる具体的な句にする
- **箇条書き**: 並列の項目（選択肢・条件・関係者）に使う。因果や条件が絡む議論を箇条書きにすると
  項目間の論理関係が消える。**議論は文章で書く**
- **番号付き**: 項目に順序があるとき（手順・優先順位・時系列）に使う。後から「2 について」と
  参照できる利点もある。順序がないものに番号を振ると、無い順序を読み手が探す
- **入れ子**: 項目に従属する条件・例外・補足があるときに使う。二段まで。
  三段目が要るなら、それは別の節に分けるべき構造
- **数を宣言したら列挙の形にする**: 「やることは三つです」と書いて散文で続けると、読み手は
  数えながら読むことになる。数を言うなら箇条書きにし、散文で書くなら数を言わない
- **強調**: 一つの節に一、二箇所まで。誤読を防ぐ否定と、節の結論に限る

## 段階6: 節ごとに書く

アウトラインの節を一つずつ埋める。全文を一息に書かない。

- 一つの節に一つのトピックだけを置く
- 段落の最初の文を読めば、その段落が何の話か分かるようにする
- 段落の先頭だけを繋げて読んでも筋が通るようにする

文と分量は、後掲の**書き方の規範**に従う。

## 段階7: 評価する

**上の層から順に見る。落ちた層で止め、その層まで戻って直す。** 下の層を先に直しても、上の層が
変われば書き直しになる。

各層の「必ず見る」を先に通す。そこが通ってから、余裕があれば残りを見る。

**層1: 文意**
1. 中心文を一文で言えるか
2. 中心文が、段階2 で決めた目的と噛み合っているか
3. 支える主張が三つ以内で、中心文の言い換えが混ざっていないか

**層2: 構造**
1. 枠と中心文が冒頭にあるか
2. 見出しだけを順に読んで筋が通るか
3. 総量が読者層の予算内か。超えていたら、文ではなく節を削る

余裕があれば: 「知らなくてよい」に分類した内容が本文に残っていないか。

**層3: 節**
1. 一つの節が一つのことを言っているか
2. 各文を一つずつ消してみて、消しても読み手が失うものを言えない文が残っていないか
3. 例示が具体的な文面になっているか。抽象的な分類の列挙で済ませていないか

余裕があれば: 段落の最初の文で話題が分かるか。箇条書きの項目が本当に並列で独立しているか。

**層4: 文**
1. 主名詞の前に修飾節が二つ以上積まれていないか
2. 一文に複数の用件が入っていないか
3. 相対日付（「来週」「明後日」）が残っていないか → 絶対日付に直す

余裕があれば: 依頼と期限の箇所に主語のない述語がないか。否定形が残っていないか。文を割った箇所で
接続の語が落ちていないか。読者層にとって未定義の語がないか。事実・伝聞・推測が区別されているか。

**層5: 全体**
1. 分量に見合う情報が入っているか。同じ長さでもっと多くを伝えられないか
2. 行動が要るなら、誰が・何を・いつまでに、を指差せるか。要らないなら、そう書いてあるか
3. 読者層の既存の立場と衝突する主張があるか。あるなら合意できる事実から始まっているか

余裕があれば: 同じ主張の繰り返しがないか。調子に頼った表現がないか。人ではなく事象を指しているか。

### 日付の検証

締切・期限は `python3` で絶対日付を確定し、平日かを検証する。土日なら前の金曜か翌週の月曜へ
寄せ、インライン注記を付ける。「before X / 〜前に」は −1 日と断定せず、自分の解釈を本文に
明示する（例:「木曜まで＝水 YYYY-MM-DD 中と解釈。木曜当日の意図なら指摘を」）。

## 段階8: 出力する

素材から確実に言えない箇所には、ラベル付き角括弧プレースホルダを置く。散文で濁さない。
`[日付A: 相手チームの提案日]` `[金額: 見積もり待ち]` `[要確認: この数値は素材に根拠なし]`

発信するのは人間であり、検証の責任も人間にある。どこを確かめるべきか分からない下書きを渡さない。

```markdown
## 本文

（そのまま使える状態）

## 確かめる項目

- [日付A: ...] — 何を入れるか
- 〇〇の数値は未検証（素材に根拠なし）

## 想定した読み手

<一行要約>（違っていれば指摘してください。プロファイルを直します）
```

「想定した読み手」の一行要約は必須。外れていれば人間が一秒で気づけるので、質問を減らしながら
誤った前提での生成を防げる。

## 書き方の規範

段階6 で使う。

### 分量は情報量に見合わせる

読み手が長い文章に付き合う忍耐は、書き手が思っているより低い。判定の基準は長さそのものではなく、
**その分量に見合う情報が入っているか**である。

**自明な文を書かない。** 読み手がその時点で既に推論できることを書いても、情報は増えず分量だけ増える。

```
悪い例: 使いたい人は使えます。（入れ方を書いてあれば自明）
悪い例: 詳細は以下のとおりです。（以下に詳細が続くのは見れば分かる）
悪い例: ご不明な点があればお問い合わせください。（連絡先を知っている相手には自明）
```

**例は具体的な文面で出す。** 抽象的な言い換えは例として働かない。

```
悪い例: してほしいことが書いていない、期限が「来週」のまま、背景と依頼が一文に混ざっている
良い例: 「例の件、確認お願いします」→「決済画面のエラー調査をお願いします。
        明日の定例までに原因の見当がつくと助かります」
```

悪い例は分類を三つ並べているだけで、読み手はどんな文面なのか想像できない。
**具体的に書けないなら、例そのものを省く。** 抽象的な例は、無いより悪い。

**一つの主張に一つの根拠。** 同じ主張を支える根拠を二つ以上並べない。読み手は一つ目で納得するか
しないかが決まっていて、二つ目以降は分量だけを増やす。

### 修飾の置き方

日本語で誤読が起きる原因はほぼ二つ、**係り受けの取り違え**と**一文に複数の用件が入ること**。
修飾の置き方で前者を潰す。規則は三つある。

**1. 主名詞の前に修飾節を積まない。**

```
悪い例: 決済画面で、先週のリリース以降に発生している、原因が API 側にあると見られる
        エラーの調査をお願いします。
良い例: 決済画面のエラー調査をお願いします。先週のリリース以降に発生していて、
        API 側が原因と見ています。
```

悪い例では「エラー」という主名詞に到達するまで、読み手は三つの修飾を宙吊りで保持し続ける。
英語の契約書を対象にした研究では、処理を難しくしている最大の要因は専門用語ではなく、文の途中に
節を挟み込む構造（中央埋め込み）だった。**日本語でも連体修飾の積み重ねが同じ負荷を生むと考えて
いるが、これは推論で、日本語での追試は確認していない。**

修飾節が二つ以上付くなら、文を分けて後ろの文へ出す。受動態も同じ理由で避ける
（「調査が行われる」より「誰が調査する」と書く）。

**2. 修飾は長いものを先、短いものを後に置く。**

```
悪い例: 至急先週の障害で影響を受けた顧客のリストを共有してください。
良い例: 先週の障害で影響を受けた顧客のリストを、至急共有してください。
```

悪い例では「至急」が「影響を受けた」にかかるのか「共有して」にかかるのか、読み手が一度止まる。

**3. 読点は長い修飾の境界に打つ。**

```
悪い例: 来週の定例で決める予定だった料金改定の方針を今日中に決めたいです。
良い例: 来週の定例で決める予定だった料金改定の方針を、今日中に決めたいです。
```

長い修飾語が二つ以上あるときはその境界に打つ。原則の語順と逆にしたときにも打つ。
息継ぎで打つと係り受けの手がかりが薄まる。

### 一文に一つの用件

```
悪い例: 先週リリースした決済画面でエラーが出ていて、原因は API 側らしいので、
        調査をお願いしたいのですが、明日の定例までに分かると助かります。
良い例: 決済画面のエラー調査をお願いします。明日の定例までに原因の見当がつくと助かります。
        先週のリリース後から発生していて、API 側が原因と見ています。
```

**ただし短くすること自体を目的にしない。** 文を割るときに接続の語（だから、ただし、そのため）まで
落とすと論理関係が消え、理解は下がる。割ったら接続を明示して繋ぎ直す。

**前提知識が低い読者層ほど、一文を短くする。** 数値の目安は読者層によって変わるので固定しない。

### 既知の情報を文頭に、新しい情報を文末に置く

```
悪い例: 新しい承認フローを、先週の障害の再発防止として導入します。
良い例: 先週の障害の再発防止として、新しい承認フローを導入します。
```

読み手は文の前半を手がかりに記憶の該当箇所を探し、そこへ後半の新情報を接続する。この順を崩すと、
同じ内容でも読む時間が伸びる。文末は最も注目される位置なので、**持ち帰ってほしい内容を文末に置く**。
主語と述語は離しすぎない。

### 否定形は肯定形に書き換える

```
悪い例: 金曜までに返信がない場合は、進めないでください。
良い例: 金曜までに返信があれば進めてください。返信がなければ止めてください。
```

否定文は肯定文より読む時間が長く、誤り率も高い。二重否定はさらに悪い。

### 調子に頼らない

皮肉、冗談めかした催促、含みのある言い回しを使わない。**書き手は自分の意図が伝わる度合いを
大きく過大評価する。** 自分の頭の中で意図した調子をつけて読み返してしまうためで、受け手の判別は
ほぼ偶然の水準だったという実験結果がある。伝えたい態度は、調子ではなく文として書き出す
（「急かす意図はありません」「これは確認で、やり直しの依頼ではありません」）。

### 事実と意見を書き分ける

観測した事実、他者の主張、自分の推測を文末で区別する（「〜だった」「〜と聞いた」「〜だと思う」）。
確認していないことを確認したように滑らかに書かない。

### 避ける表現

- **予告**: 「重要なのは〜です」「〜について共有させていただきます」——主張をそのまま書く
- **空虚な形容**: 「抜本的」「包括的」「根本的」——何がどうなのかを書く
- **無生物主語の擬人化**: 「このデータが示しているのは」→「このデータから分かるのは」
- **英語慣用句の直訳**: 「開かれた問い」→「まだ答えが出ていない」、「〜が効く」→ 効果の中身を書く
