# 読みやすく分かりやすい文章を書く

**担う**: 読者の特定、目的の設定、文意の決定、構造の設計、文の組み立て、工程ごとの評価。

**担わない**: 素材にない事実・数値・主張を作ること。内容は呼び出し側の文脈から来る。

## 読み手に起きる三つのこと

以下の規則はすべてここから出る。**個別の規則を思い出せないときは、原理から導く。**

1. **予測しながら読む。** 見当がついていれば速く正確に読み、外れた箇所で止まる。
2. **同時に保持できる量は少ない。** 宙吊りの要素が増えるほど取り違えと読み落としが増える。
3. **途中で降りる。** 最後まで読む保証はない。

## 五つの工程を順に進め、直すときは上流へ戻る

**読者と目的 → 文意 → 構造 → 節 → 文。**

一度に全文を書かない。前の工程が決まってから次へ進む。各工程の末尾に、その工程が残すアウトプットと、
次へ進む条件を置いてある。**条件に落ちたらその場で直し、下流へ進まない。** 通してから次の工程に入る。

**直すときは、直す必要が生じた工程まで戻り、そこから下を作り直す。** 下流をいくら直しても、上流が
間違っていれば直らない。書いている途中で上流が変わるのは普通に起きるので、そのときも同じ。

**条件は読み返しではなく操作で確かめる。** 自分の文章を読み返すと、書いたときの意図が補われて
条件が通ってしまう。見出しだけを抜き出して並べる、文を一つ消してみる、相対表現を検索する、
日付を `python3` に計算させる。文章から離れる操作に置き換えられる条件は、置き換えてから判定する。

**同じ工程で二度落ちたら、一つ上の工程を疑う。** 直し方が悪いのではなく、上流から渡された
アウトプットがその工程で扱える形になっていない。

慣れた型の短い文章では、工程2 と工程3 を頭の中で済ませてよい。

## 工程1: 読者と目的

### 読み手を決める

**読み手が指定されていなければ、用件から推定する。聞かない。** 推定して書いたものは、外れていれば
人間が下書きを見ながら一秒で訂正できる。聞くと必ず一往復かかるが、推定は当たれば往復ゼロで、
外れたときだけ作り直しになる。作り直しは人間の往復より安い。

**読み手の範囲は、その文章が誰の判断や作業を変えるかで決める。** 書き手の所属チームで決めない。
「チームに共有」「みんなに周知」のような曖昧な指定は、そのまま受け取ると書き手の隣の席までしか
届かない。技術的な決定でも、それが施策の設計や運用のやり方を変えるなら、企画する側も読者に入る。

読み手がどうしても読み取れないときは、**最も条件の厳しい層**（前提知識が低く、読む量の予算が
小さい）に向けて書く。

決まったら、**役割から推定できるものは推定してよい**。前提知識・関心・読む量の予算・読み方の好みは、
役割（PdM・エンジニア・全社・社外）からの一般論で足りる。社外の読み手には、社内の固有名詞と略語が
通じない前提で書く。推定した内容は出力の「想定した読み手」に
添えて、外れていれば訂正してもらう。

読み手は個人とは限らない。チーム・部門・全社・不特定多数も読者層であり、**個人は「一人しかいない
読者層」として同じに扱う**。集団は各項目が一点に決まらないので、**前提知識と読む量の予算は最も
条件の厳しい層に合わせる**（平均に合わせると、下限の人が落ちたことに誰も気づかない）。
**立場が割れている論点は「割れている」と書き、一つに丸めない**。

読み手が複数の層にまたがるときは、質問せず構造で解く。層ごとに区画を分け、どこまで読めばよいかを
本文に書く。外部の個人はコードネームで扱い、氏名・連絡先を書かない。

### 推定してはいけないもの

**この話題について過去に何が決まっているかは、推定せず素材から探す。** 役割からの一般論では出てこず、
外すと決まった話を蒸し返す文章になる。探す先は `learnings/`、`worklog/`、`organizations/digest/`、
相手が社内メンバーなら `people/members/<name>/`。

見つかった決定は、読者が既に共有している前提として扱い、そこへ接続する形で書く。衝突する主張を
書くなら、合意できる事実から始める。

### 目的を決める

**読み終えた読者がどうなっているかを一文で書く。** これが以降の全判断の基準になる。

```
悪い例: 新しい skill について説明する
良い例: 読み終えた読者が、この skill を自分で試すか見送るかを判断できている
```

| 種類 | 読み終えた読者の状態 | 必要な要素 |
|---|---|---|
| **承認を求める**（決裁依頼・稟議・相談） | 承認するか差し戻すかを決められる | 決めてほしいこと・期限・選択肢と推奨・影響とコスト |
| **実作業を求める**（依頼・アサイン） | 何をどうすればよいか分かっている | してほしいこと・期限・前提と手順・完了条件・断る場合の選択肢 |
| **判断を共有する**（決定・報告） | 何が決まったか・なぜかを説明できる | 決めたこと・理由・却下案とその理由・影響範囲・決定者と委任度・異論の期限 |
| **理解させる**（説明・解説・記事） | 対象を自分の言葉で説明できる | 中心となる考え・支える根拠・具体例・限界 |
| **記録する**（議事・ログ・手順） | 後から探して同じ結論に到達できる | 事実・日付・決定と保留・参照先 |

委任度は「自分が決めた／チームの提案を自分が承認した／チームが決めた」。これが無いと読者は関与
できるのか判断できず、決まった話が後から蒸し返される。

### 何を載せ、何を落とすか決める

素材を三つに分ける。**基準は「読者の判断を変えるか」。**

- **既知**: 読者が既に知っている。説明せず、文脈の足がかりとして使う
- **知るべき未知**: 判断を変える。本文に置く
- **知らなくてよい**: 判断を変えない。**落とす**

目的の種類を基準にしない。目的を一つに絞ると副次的な目的が要求する要素まで落ちる。説明が目的でも、
読者が導入の可否を決める立場なら工数は判断を変えるので残す。

```
落とす: 「調べたところ、A 案と B 案が見つかりました。A 案は〇〇のため見送り、B 案を採りました」
残す:  「B 案で進めます」（判断の共有が目的なら A 案の却下理由まで残す）

落とす: 「Bransford & Johnson (1972) の実験では、題を読む前に与えた群だけ理解が向上しました」
残す:  「最初の一文に用件を書いてください」
```

**根拠と出典は本文に書かない。** 読者が検証を求める立場にいるときだけ末尾かリンクに置く。

橋渡しを厚くすると前提知識の低い読者は助かるが、高い読者ではかえって理解が下がる。
**既定は「迷ったら明示する」**とし、高いと分かっている層でだけ減らす。

### 工程1 の出口

**アウトプット**: 読み手の一行（役割・前提知識・読む量の予算）、目的の一文、素材の三分類。

**次へ進む条件**

1. 読み手が一つに定まり、推定した項目を出力に添えられる形になっているか
2. 目的が「読み終えた読者の状態」として一文で書けているか
3. この話題について過去に決まっていることを素材から探したか
4. 素材が三つに分かれ、**落とすものを名指しできるか**

## 工程2: 文意

**この文章が言いたいことを一文で書く。** 書けないなら、まだ書き始める段階にない。

この一文を「中心文」と呼ぶ。支える主張は**三つまで**。原理2 により、読者が同時に保持できる筋は
限られる。四つ以上出てきたら、そのいくつかは中心文の言い換えか、別の文章にすべき内容である。

```
中心文: 文章の伝達の失敗は、書き手に見えにくいだけで原因はほぼ決まっている
支える主張1: 相手に何をしてほしいか書いていない
支える主張2: 期限が相対表現のまま残っている
支える主張3: 背景と依頼が一文に混ざっている
```

### 工程2 の出口

**アウトプット**: 中心文の一文と、支える主張の箇条書き（三つまで）。

**次へ進む条件**

1. 中心文を一文で言えるか
2. 中心文が工程1 の目的と噛み合っているか
3. 支える主張が三つ以内で、中心文の言い換えが混ざっていないか

## 工程3: 構造

**見出しレベルまでの階層アウトラインを作ってから書く。** 思いつきを並べるだけでは質が変わらず、
階層にして初めて効く。

1. **分量の予算を決める**。読者層の「読む量の予算」から節の数と節あたりの長さを逆算する。
   予算が小さいなら支える主張を減らす。**削るのは節であって文ではない**
2. **枠を先頭に置く**（下記）
3. **中心文を枠の直後に置く**。経緯・背景・検討過程は後ろへ回す（原理3）
4. **見出しだけを読んで筋が通るか確かめる**。通らないなら順序か粒度が間違っている

### 枠

読み始める前に、これが何の文章かを渡す。**読む前に与えたときだけ効果があり、読んだ後では効かない**
（原理1: 予測の材料は先にしか効かない）。末尾に「というわけで承認をお願いします」と書く構成は、
そこに至るまで何を判断しながら読めばよいか分からない状態を作る。

形は媒体で変える。Slack は角括弧ラベルと一文（`【相談】料金改定について、今週中に意見をください。`）、
文書は表題の直下に一文、メールは件名と冒頭一文。

種類のラベルが要るのは、読者に行動や判断が求められる文章だけ。説明や解説では表題と冒頭の一文で
対象と範囲が分かれば足りる（`Kotlin の coroutine のキャンセル処理について、実装で踏みやすい
落とし穴を書きます。`）。

### 見出し・箇条書き・強調

構造を目に見える形にすると切れ目を掴めるが、拾い読みを促す副作用がある。**見出しを増やすと拾える
話題は増え、各話題の中身の記憶は減る。** 深く理解してほしい文章では見出しを増やさない。

- **見出し**: 話題が三つ以上あるときだけ付ける。内容を特定できる具体的な句にする
- **箇条書き**: 並列の項目（選択肢・条件・関係者）に使う。因果や条件が絡む議論は文章で書く。
  箇条書きにすると項目間の論理関係が消える
- **番号付き**: 順序があるとき（手順・優先順位・時系列）に使う。順序がないものに番号を振ると、
  無い順序を読み手が探す
- **入れ子**: 項目に従属する条件・例外があるときだけ。二段まで。三段目は別の節に分けるべき構造
- **数を宣言したら列挙にする**: 「やることは三つです」と書いて散文で続けると、読み手は数えながら
  読むことになる。数を言うなら箇条書きにし、散文で書くなら数を言わない
- **強調**: 一つの節に一、二箇所まで。増やすほど一箇所あたりの効果が薄まる

### 工程3 の出口

**アウトプット**: 見出しレベルまでの階層アウトラインと、先頭に置く枠の一文。

**次へ進む条件**

1. 枠と中心文が冒頭にあるか
2. 見出しだけを順に読んで筋が通るか
3. 総量が読者層の予算内か。超えていたら節を削る

## 工程4: 節

- 一つの節に一つのトピックだけを置く
- 段落の最初の文を読めば、その段落が何の話か分かるようにする（原理1）
- 段落の先頭だけを繋げて読んでも筋が通るようにする（原理3）

### 分量は情報量に見合わせる

判定の基準は長さではなく、**その分量に見合う情報が入っているか**。

**自明な文を書かない。** 読み手がその時点で既に推論できることを書いても、情報は増えず分量だけ増える。

```
悪い例: 使いたい人は使えます。（入れ方を書いてあれば自明）
悪い例: ご不明な点があればお問い合わせください。（連絡先を知っている相手には自明）
```

**例は具体的な文面で出す。** 抽象的な言い換えは例として働かない。

```
悪い例: してほしいことが書いていない、期限が「来週」のまま、背景と依頼が一文に混ざっている
良い例: 「例の件、確認お願いします」→「決済画面のエラー調査をお願いします。
        明日の定例までに原因の見当がつくと助かります」
```

具体的に書けないなら例そのものを省く。抽象的な例は無いより悪い。

**一つの主張に一つの根拠。** 読み手は一つ目で納得するかしないかが決まっていて、二つ目以降は
分量だけを増やす。

### 工程4 の出口

**アウトプット**: アウトラインの各節が埋まった本文。

**次へ進む条件**

1. 一つの節が一つのことを言っているか
2. 各文を一つずつ消してみて、消しても読み手が失うものを言えない文が残っていないか
3. 例示が具体的な文面になっているか

## 工程5: 文

日本語で誤読が起きるのは、ほぼ**係り受けの取り違え**と**一文への意図の詰め込み**による。
どちらも原理2 の現れで、機械的に潰せる。

### 修飾の置き方

**主名詞の前に修飾節を積まない。** 主名詞に到達するまで修飾を宙吊りで保持させることになる。
二つ以上付くなら文を分けて後ろへ出す。受動態も同じ理由で避ける（「調査が行われる」より
「誰が調査する」）。

```
悪い例: 決済画面で、先週のリリース以降に発生している、原因が API 側にあると見られる
        エラーの調査をお願いします。
良い例: 決済画面のエラー調査をお願いします。先週のリリース以降に発生していて、
        API 側が原因と見ています。
```

**長い修飾を先、短い修飾を後に置く。** 下の悪い例では「至急」が「影響を受けた」にかかるのか
「共有して」にかかるのか、読み手が一度止まる。**読点は長い修飾の境界に打つ**（二つ以上あるとき、
および原則の語順と逆にしたとき）。息継ぎで打つと係り受けの手がかりが薄まる。

```
悪い例: 至急先週の障害で影響を受けた顧客のリストを共有してください。
良い例: 先週の障害で影響を受けた顧客のリストを、至急共有してください。
```

### 一文に一つの意図だけ書く

一文が担う意図は一つにする。工程2 の文意が文章全体の意図で、各文はその構成要素として一つの意図を
担う。意図の実体は文書型で変わり、依頼なら用件、説明なら主張、記録なら事実にあたる。

```
悪い例: 先週リリースした決済画面でエラーが出ていて、原因は API 側らしいので、
        調査をお願いしたいのですが、明日の定例までに分かると助かります。
良い例: 決済画面のエラー調査をお願いします。明日の定例までに原因の見当がつくと助かります。
        先週のリリース後から発生していて、API 側が原因と見ています。
```

**短くすること自体を目的にしない。** 文を割るときに接続の語（だから、ただし、そのため）まで落とすと
論理関係が消え、理解は下がる。割ったら接続を明示して繋ぎ直す。前提知識が低い読者層ほど短くする。

### 既知の情報を文頭に、新しい情報を文末に置く

```
悪い例: 新しい承認フローを、先週の障害の再発防止として導入します。
良い例: 先週の障害の再発防止として、新しい承認フローを導入します。
```

読み手は文の前半を手がかりに記憶の該当箇所を探し、そこへ後半を接続する（原理1）。この順を崩すと、
同じ内容でも読む時間が伸びる。文末は最も注目される位置なので、持ち帰ってほしい内容を文末に置く。
主語と述語は離しすぎない。

### 否定形は肯定形に書き換える

```
悪い例: 金曜までに返信がない場合は、進めないでください。
良い例: 金曜までに返信があれば進めてください。返信がなければ止めてください。
```

否定を理解するには、否定される肯定命題を組み立ててから反転する必要がある（原理2）。二重否定は
さらに悪い。

### 書いていないことは伝わらない

- **伝えたい態度は文として書き出す**。含みや言い回しでは伝わらない（「急かす意図はありません」
  「これは確認で、やり直しの依頼ではありません」）
- **事実と意見を書き分ける**。観測した事実、他者の主張、自分の推測を文末で区別する
  （「〜だった」「〜と聞いた」「〜だと思う」）。確認していないことを確認したように書かない

### 中身のない語を使わない

- **予告**: 「重要なのは〜です」「〜について共有させていただきます」——主張をそのまま書く
- **空虚な形容**: 「抜本的」「包括的」「根本的」——何がどうなのかを書く
- **無生物主語の擬人化**: 「このデータが示しているのは」→「このデータから分かるのは」
- **英語慣用句の直訳**: 「開かれた問い」→「まだ答えが出ていない」、「〜が効く」→ 効果の中身を書く

### 日付は絶対値で書く

締切・期限は `python3` で絶対日付と曜日を確定する。そのうえで**土日と祝日の両方**を外す。
土日なら前の金曜か翌週の月曜へ寄せ、インライン注記を付ける。

**祝日は `python3` では分からないので、その年の暦を明示的に確認する。** 特に祝日に挟まれた平日が
休日になる（国民の休日）場合を見落としやすい。例として 2026 年は 9-21 が敬老の日、9-23 が秋分の日で、
間の 9-22 が国民の休日になり、9-18（金）の次の営業日は 9-24（木）になる。

「before X / 〜前に」は −1 日と断定せず、自分の解釈を本文に明示する
（例:「木曜まで＝水 YYYY-MM-DD 中と解釈。木曜当日の意図なら指摘を」）。

### 工程5 の出口

**アウトプット**: そのまま渡せる状態の全文。

**次へ進む条件**

1. 主名詞の前に修飾節が二つ以上積まれていないか
2. 一文に複数の意図が入っていないか
3. 相対日付（「来週」「明後日」）が残っていないか → 絶対日付に直す

---

## 全体の合否

工程ごとの条件は、その工程の中だけを見る。最後に全文を通して読み、**工程を跨がないと見えない三つ**を
確かめる。落ちたら、原因になっている工程まで戻る。

1. **分量に見合う情報が入っているか。** まず工程1 で落とすと決めた素材が本文に残っていないかを見る。
   残っていないのに長いなら、原因は構造（工程3）にある
2. **行動が要るなら、誰が・何を・いつまでに、を指差せるか。** 要らないなら、要らないと書いてあるか
3. **読者の既存の立場と衝突する主張があるなら、合意できる事実から始まっているか**

---

## 出力

素材から確実に言えない箇所には、ラベル付き角括弧プレースホルダを置く。散文で濁さない。
`[日付A: 相手チームの提案日]` `[金額: 見積もり待ち]` `[要確認: この数値は素材に根拠なし]`

発信も検証も人間の責任なので、どこを確かめるべきか分からない下書きを渡さない。

```markdown
## 本文

（そのまま使える状態）

## 確かめる項目

- [日付A: ...] — 何を入れるか
- 〇〇の数値は未検証（素材に根拠なし）

## 想定した読み手

<一行要約>（違っていれば指摘してください）
```

「想定した読み手」の一行要約は必須。外れていれば人間が即座に気づけるので、質問を減らしつつ
誤った前提での生成を防げる。

## 完了

**完了条件**: 五つの工程の「次へ進む条件」と全体の合否を通し、上の三点が揃っていること。

**完了処理**: 想定した読み手を訂正されたら、文を直さずに工程1 へ戻って作り直す。読み手が変われば
載せる素材も構造も変わるので、下流だけ直すと元の読み手に向けた文章がそのまま残る。
