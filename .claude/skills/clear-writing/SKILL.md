# 分かりやすい文章を書く

## この skill が担う範囲

**担う**: 用件の取捨選択と配置、そして日本語の文の組み立て。誰に何を見せ、何を落とし、どの順で置くか。

**担わない**: 何を言うか。主張・判断・事実は呼び出し側の文脈から来る。素材にないことを補って書かない。

伝達の失敗（読まれない・誤解される・受け入れられない・行動されない）を防ぐのが目的であり、
主張の鋭さを上げる仕組みではない。

## 入力

| 入力 | 既定の取り方 |
|---|---|
| 用件（素材） | 呼び出し側の文脈・会話・貼られた資料から取る |
| 読み手（読者層） | Step 1 で特定する。個人・チーム・全社・不特定多数のいずれか |
| 起こしたいこと | 承認・意見・着手・共有のいずれかを用件から推定する |
| 媒体 | Slack / 文書 / メール。用件と読み手から推定する |
| 文体見本 | 発信者の過去の文章。なければ会話中の発言を見本にする |

**人間に質問してよいのは次の三つが読み取れないときだけ。** それ以外は推定し、推定内容を出力に添えて
人間が訂正できる形にする。質問は往復を増やす操作であり、この skill が減らそうとしているものと同じもの。

1. 読み手が決裁者か実行者か（結論の粒度と根拠の深さが変わる）
2. この文章が依頼・決定・相談・共有のどれか（相手に求める行動が変わる）
3. 社内向けか社外向けか（前提の共有度と表現の制約が変わる）

この三つは外れると構成ごと書き直しになる。用語を知っているかどうか等の細部は、外れても一文の補足で
回復できるので質問しない。

## Step 1: 読者層を特定する

読み手は個人とは限らない。チーム・部門・全社・不特定多数も読者層であり、
**個人は「一人しかいない読者層」として同じ形式で扱う。**

プロファイルは `audiences/<id>.md` の一箇所にある。発信者自身が読み手の場合も同じ。
該当するものが無ければ素材から作り、同じ場所に保存してから使う。
読み手を特定できないときは `audiences/general.md` を使う。**必ずどれか 1 つに着地させる。**

素材元は読者層によって違う。丸写しせず、下の 7 項目に絞って抽出する。

| 読者層 | 素材元 |
|---|---|
| 社内メンバー個人 | `people/members/<name>/`（1on1 の蓄積、特に「最近の傾向」） |
| 発信者自身 | `profile/` |
| 社内の集団 | `organizations/`、そのチャンネルの過去ログ、定例の議事録 |
| それ以外 | 過去のやり取り（Slack・議事録・PR コメント） |

プロファイルの項目は七つ。

- **役割と責務**: 何の判断をする層か
- **前提知識**: どの領域の語が説明不要か / 何が未知か
- **関心**: 判断のときに真っ先に見る観点
- **読む量の予算**: どの媒体でどれくらい読む層か
- **既存の立場**: 過去の発言・決定・反対した経緯
- **関係**: やり取りの頻度と距離、過去の摩擦
- **読み方の好み**: 結論だけ欲しいか、経緯も要るか

### 集団を扱うときの二つの規則

個人は各項目が一点に決まるが、集団は分布を持つ。潰し方を固定する。

1. **前提知識と読む量の予算は、最も条件の厳しい層に合わせる。** 平均ではなく下限。
   平均に合わせると、下限の人が落ちたことに誰も気づかない。
2. **立場が割れている論点は「割れている」と書き、一つに丸めない。**
   割れている論点を含む文章は合意できる事実から始める必要があり、Step 3 の構成が変わる。

埋まらない項目は空のままにし、推定で埋めない。

**外部の個人**（候補者・社外の担当者など）はコードネームで管理し、氏名・連絡先をファイルに書かない。
プロジェクト側の PII 規約があればそれに従う。

**更新**: 推定が外れたと分かったとき（人間に訂正されたとき・相手の反応が想定と違ったとき）は、
プロファイルの「推定が外れた記録」に一行追記してから終わる。これをやらないと初期値のまま古びる。

## Step 2: 取捨選択

用件の要素を一つずつ「この読者層がこの判断をするのに必要か」で仕分ける。

- **必要**: 本文に置く
- **不要だが参照されうる**: リンク・付録・スレッドの下に出す
- **不要**: 落とす

材料を全部並べるのはこの工程をやっていない状態。落とした要素は捨てるのではなく、
本文の外に移して負荷だけを下げる。

## Step 3: 枠を先頭に置き、型に配置する

### 枠は必ず先頭（この skill で最も効果の大きい一手）

**読み手が本文を読み始める前に、これが何の文章かを渡す。** 具体的には二つ——
**文書の種類**（依頼・決定・相談・共有）と、**相手に起きてほしいこと**。

Bransford & Johnson (1972) は、同じ文章でも「これは何の話か」を**読む前に**与えた群だけが
理解・再生とも向上し、**読んだ後に与えた群には効果がなかった**ことを示した。枠は後から足しても
効かない。末尾に「というわけで承認をお願いします」と書く構成は、そこに至るまで読み手が
何を判断しながら読めばよいか分からない状態を作る。

形は媒体で変える。中身（種類＋求める行動）は変えない。

| 媒体 | 枠の形 | 例 |
|---|---|---|
| Slack | 角括弧ラベル＋一文 | `【相談】料金改定の方針について、今週中に意見をください。` |
| 文書 | 表題の直下に一文 | `この文書は〇〇の設計方針を決めるためのものです。読者に判断は求めません。` |
| メール | 件名＋冒頭一文 | `Subject: 【依頼】〇〇の承認（6/12 まで）` |

「これは相談ですが」と地の文に埋めるより、ラベルとして切り出すほうが拾い読みで落ちない。
ただし読み手が一人で関係が近い場合、ラベルは硬く見えることがある。その場合は
「相談させてください。〇〇の方針を決めたいのですが」のように**一文目で種類が分かれば**よい。

**対応不要な共有にも枠を置く。** 「【共有・対応不要】」は読み手の負荷を最も下げるラベル。

### 型

用件の種類に応じて構成を固定する。型があるぶん出力がばらつかない。

**依頼**
1. してほしいこと（一文）
2. 期限
3. 判断に必要な前提
4. 断る・変更する場合の選択肢

**決定**
1. 決めたこと
2. その理由
3. 却下した案とその理由
4. 影響範囲
5. 対応不要な人への明示

**相談**
1. 論点
2. 現時点の推奨
3. 迷っている点
4. 相手に答えてほしいこと（具体的に）

**共有**
1. 結論
2. 関係する人
3. 対応不要の明示

### 重点先行

枠の次には結論を置く。読み手は上から順に読み、下に行くほど読まれない
（NN/g の視線計測では F 型の読み方になり、長いページの下端まで到達しない読者が多い）。
経緯・背景・検討過程は結論の後ろに回す。木下是雄が「重点先行主義」と呼んだ配置と同じ。

### 段落

- 一つの段落に一つのトピックだけを置く
- 段落の最初の文を読めば、その段落が何の話か分かるようにする
- 拾い読みされても筋が通るように、段落の先頭だけを繋げて読める状態にする

表は標準 Markdown テーブルで書く。罫線の ASCII アートは環境でレイアウトが崩れる。

## Step 4: 日本語の文を組み立てる

日本語で誤読が起きる原因はほぼ二つ、**係り受けの取り違え**と**一文に複数の用件が入ること**。
機械的に潰せる。

### 修飾は長いものを先、短いものを後に置く

```
悪い例: 至急先週の障害で影響を受けた顧客のリストを共有してください。
良い例: 先週の障害で影響を受けた顧客のリストを、至急共有してください。
```

悪い例では「至急」が「影響を受けた」にかかるのか「共有して」にかかるのか、読み手が一度止まる。
本多勝一『日本語の作文技術』の原則——節を句より前に、長い修飾を短い修飾より前に置く。

### 読点は長い修飾の境界に打つ

```
悪い例: 来週の定例で決める予定だった料金改定の方針を今日中に決めたいです。
良い例: 来週の定例で決める予定だった料金改定の方針を、今日中に決めたいです。
```

長い修飾語が二つ以上あるときはその境界に打つ。原則の語順と逆にしたときにも打つ。
それ以外の読点は減らす。息継ぎで打つと係り受けの手がかりが薄まる。

### 一文に一つの用件

```
悪い例: 先週リリースした決済画面でエラーが出ていて、原因は API 側らしいので、
        調査をお願いしたいのですが、明日の定例までに分かると助かります。
良い例: 決済画面のエラー調査をお願いします。明日の定例までに原因の見当がつくと助かります。
        先週のリリース後から発生していて、API 側が原因と見ています。
```

依頼・期限・背景を一文に混ぜると、読み手はどれが求められていることか判断できない。
求める行動を単独の文にし、背景は後ろの文に分ける。

### 事実と意見を書き分ける

木下是雄が理科系の作文で最重要とした区別。観測した事実、他者の主張、自分の推測を、
文末で区別する（「〜だった」「〜と聞いた」「〜だと思う」）。
確認していないことを確認したように滑らかに書かない。

### 避ける表現

- **予告**: 「重要なのは〜です」「〜について共有させていただきます」——主張をそのまま書く
- **空虚な形容**: 「抜本的」「包括的」「根本的」——何がどうなのかを書く
- **無生物主語の擬人化**: 「このデータが示しているのは」→「このデータから分かるのは」
- **英語慣用句の直訳**: 「開かれた問い」→「まだ答えが出ていない」、「〜が効く」→ 効果の中身を書く

## Step 5: 関門の順に検査する

関門は順序を持つ。前の関門で落ちた文章は、後ろの特性がどれだけ高くても評価されない。
**落ちた関門の項目だけ直して再検査し、下流の関門には進まない。**

**関門1: 読まれるか**
- 冒頭に枠（文書の種類＋求める行動）があるか
- 結論が枠の直後にあるか
- 総量が読者層の予算内か

**関門2: 理解されるか**
- 依頼と期限の箇所に、主語のない述語がないか
- 相対日付（「来週」「明後日」）が残っていないか → 絶対日付に直す
- 読者層にとって未定義の語・略語がないか
- 一文に複数の用件が入っていないか
- 事実・伝聞・推測が文末で区別されているか

**関門3: 受け入れられるか**
- 読者層の既存の立場と衝突する主張を含むか。含むなら合意できる事実から始まっているか
- 人ではなく事象を指しているか
- 批判や催促でないなら、そうでないと書いてあるか

**関門4: 行動できるか**
- 誰が・何を・いつまでに、を本文から指差せるか
- 行動が不要なら「対応不要」と書いてあるか

### 日付の検証

締切・期限を書くときは `python3` で絶対日付を確定し、平日かどうかを検証する。土日に当たる場合は
前の金曜か翌週の月曜へ寄せ、インライン注記を付ける。

「before X / 〜前に」は解釈が分かれる。−1 日と断定せず、自分の解釈を本文に明示する
（例:「木曜まで＝水 YYYY-MM-DD 中と解釈。木曜当日の意図なら指摘を」）。

## Step 6: 印を付けて出力する

素材から確実に言えない箇所には、ラベル付き角括弧プレースホルダを置く。散文で曖昧に濁さない。

- `[日付A: 相手チームの提案日]`
- `[金額: 見積もり待ち]`
- `[要確認: この数値は素材に根拠なし]`

発信するのは人間であり、検証の責任も人間にある。どこを確かめるべきか分からない下書きを渡さない。

```markdown
## 本文

（そのまま送れる状態。冒頭に枠。件名が要る媒体なら Subject: 行）

## 送信前に埋める・確かめる項目

- [日付A: ...] — 何を入れるか
- 〇〇の数値は未検証（素材に根拠なし）

## 想定した読み手

<一行要約>（違っていれば指摘してください。プロファイルを直します）
```

「想定した読み手」の一行要約は必須。これが外れていれば人間が一秒で気づけるので、
質問を減らしながら誤った前提での生成を防げる。

## やらないこと

- 素材にない主張・事実・数値を補わない
- 品質特性のチェックリストを生成時に適用しない（枠・型・読者層プロファイルだけで書く。検査は Step 5 で別に行う）
- 短くするために必要な前提を削らない（簡潔さは「不要な文がない」ことであって「短い」ことではない）
- 読み手が複数層にまたがる場合に「どちらですか」と質問しない。層ごとに区画を分け、
  どこまで読めばよいかを本文に明示する

## 根拠

採用した技術と、その裏付け。

| 技術 | 裏付け |
|---|---|
| 枠を読む前に置く | Bransford & Johnson (1972)「Contextual prerequisites for understanding」。題を先に与えた群だけ理解・再生が向上し、後から与えた群には効果なし |
| 重点先行 | 木下是雄『理科系の作文技術』の重点先行主義。NN/g の視線計測（F 型の読み方、長文の下端に到達しない） |
| 一段落一トピック / 段落冒頭で主題 | パラグラフライティング（木下是雄、k16shikano japanese-tech-writing） |
| 修飾の順序・読点の二原則 | 本多勝一『日本語の作文技術』 |
| 事実と意見の書き分け | 木下是雄『理科系の作文技術』 |
| 翻訳調・LLM 口調の排除 | k16shikano `japanese-tech-writing`（Unlicense）から、伝達文書で頻出するものを抜粋 |

**過信しない点**: 「読む前に枠を与える」系の手法（advance organizer）のメタ分析は、
全体として促進的だが効果は一貫しない。読み手の前提知識に依存する。
枠は安価なので常に置くが、これだけで理解が保証されるとは考えない。

## 関連 skill との関係

- `japanese-tech-writing`（k16shikano, Unlicense）: 技術書・記事の原稿向け。論証の厳密さ・演出の抑制・
  段落の規範が厚い。**長い解説文を書くときはそちらが上位**。この skill は伝達文書（依頼・決定・相談・共有）が対象
- 表記揺れ（全角半角・句読点の統一）は専用の表記 skill があればそちらに任せる。この skill では扱わない
