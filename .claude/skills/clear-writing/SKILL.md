# 読みやすく分かりやすい文章を書く

**担う**: 読者の特定、目的の設定、文意の決定、構造の設計、文の組み立て、工程ごとの評価、書き上げた全文の推敲。

**担わない**: 素材にない事実・数値・主張を作ること。素材は呼び出し側の文脈から来る。
会話の返信の書き方は output style が決める。この skill は、人に渡す文章に使う。

## 前提

規則の出どころは二つ。読者がどう読むかと、筆者が何に責任を負うか。

**読者の性質。** 読みやすさの規則はここから出る。規則を思い出せないときは、この四つから導く。

1. **予測しながら読む。** 見当がついていれば速く正確に読み、外れたところで止まる。
2. **同時に保持できる量は少ない。** 宙吊りの要素が増えるほど、係り受けを取り違え、読み落とす。
3. **最後まで読むとは限らない。** 分量が予算を超えたところで降りる。
4. **戻って確かめる。** 分からないところで前へ戻り、同じ語を手がかりに該当箇所を探す。戻れないか、
   戻っても見つからないと、理解が落ちる。

**筆者の責任。** この skill が作るのは下書きで、送るのは筆者、間違いの責任も筆者が負う。だから、
どこを確かめればよいかが分かる形で渡す。素材にないことを書かない、事実と意見を書き分ける、
未確定の箇所に印を置く。この三つはここから出る。

## 七つの工程を順に進め、直すときは上流へ戻る

**読者 → 目的 → 素材 → 文意 → 構造 → 節 → 文。** 七工程を通したあと、「推敲」で全文を検査してから渡す。

**工程1〜3 は入力を整える。** この skill の入力は読者・目的・素材の三つで、素材は必ず呼び出し側の
文脈から来るが、読者と目的は欠けたまま来ることが多い。欠けていれば作り、あれば開いて確かめる。
素材だけは工程3 で増えることもある。**工程4〜7 が文章そのものを、粗いところから細かいところへ作る。**

**一つの工程が作るアウトプットは一つ。** 二つ以上を同時に作ると、後ろに置いたものほど雑になる。

**各工程のアウトプットは、その工程を終えた時点で工程ファイルへ順に追記する。** 工程ファイルは、
プロジェクトの一時ファイル置き場（規約がなければセッションの scratchpad）に、文章ごとに一つ作る。
一つの応答で複数の工程を通すと、この原則が生成の実行単位では守られない。工程ごとに書き出せば実行単位が工程に
揃い、後から本文に合わせて書き換えれば差分に出るので、辻褄合わせもできなくなる。ファイルは一つに
して上から順に足す。工程ごとに分けると、突き合わせのたびに開く数が増える。

**工程ごとにセクションを作る。工程5 は節ごとに小見出しを立て、工程6 はその下に本文を足す。**

```
## 工程5: 構造
認知フレーム: <一文>

### 1. <見出し>
一文: <この節が何を言う節か>
本文: <工程6 で書く>
```

**工程6 は一文を上書きせず、下に足す。** 一文は工程5 で決めた意図で、本文は実際に書いたもの。
消すと、推敲の逆アウトラインが実測どうしの比較になり、意図とのずれが出なくなる。工程6 の出口条件
「各節が工程5 で書いた一文と一致するか」も、上下に並んだ二行を見るだけで済む。本文は節を順に
並べたものになるので、組み直しが起きない。工程7 は新しいセクションを作らず、本文の行を直す。

**工程5 の直後で一度止め、前提とアウトラインを筆者に渡す。** 読者・目的・中心文・構造のどれが
外れても本文が丸ごと無駄になるのに対し、工程6 以降のずれは本文の一部で収まる。止める価値があるのは、
下流の作り直しが最大で、かつ訂正が短く済むこの一点だけ。短い文章（下記）では止めない。
筆者に戻せない実行（無人実行・サブエージェント）でも工程5 で止めずに最後まで進め、前提と確認事項は
呼び出し元への報告に回す。止めても訂正する人がいないので、待つだけになる。

**短い文章とは、工程1 で決めた読む量の予算が画面一つ以下か、工程4 の支える主張が一つ以下で節が
一つで足りる文章を指す。** 目安で、厳密な上限ではない。短い文章では工程5 と工程6 を頭の中で済ませてよい。
工程1〜3 は一行ずつまで畳んでよいが、三つとも書く。前提を書かずに始めると、外れていたときにどこが
原因か分からなくなる。

一度に全文を書かない。前の工程が決まってから次へ進む。各工程の末尾に、その工程が残すアウトプットと、
次へ進む条件を置いてある。**条件に落ちたらその場で直し、下流へ進まない。** 通してから次の工程に入る。

**直すときは、直す必要が生じた工程まで戻り、そこから下を作り直す。** 下流をいくら直しても、上流が
間違っていれば直らない。書いている途中で上流が変わるのは普通に起きるので、そのときも同じ。

**条件は読み返しではなく操作で確かめる。** 自分の文章を読み返すと、書いたときの意図が補われて
条件が通ってしまう。見出しだけを抜き出して並べる、文を一つ消してみる、否定形を検索する、
総量を数える。文章から離れる操作に置き換えられる条件は、置き換えてから判定する。数は `wc -m` などの
コマンドで出す（空白を除くなら `tr -d '[:space:]'` を通してから数える）。手で数えるとずれる。

**置き換えられないものは、本文だけを渡した別のエージェントに確かめさせる。** 同じ文脈で確かめると、
書いたときの意図がそのまま補われ、検査が素通りする。推敲の理解のパス・逆アウトライン・素材との
対応表がこれにあたる。立てる条件と依頼文は `references/revision.md` にある。

**同じ工程で二度落ちたら、一つ上の工程を疑う。** 直し方が悪いのではなく、上流から渡された
アウトプットがその工程で扱える形になっていない。

## 入口

**場面ごとに、どの工程から入るかを決めてから始める。** 入口を誤ると、元の文章にしかない事実が落ちるか、
要らない工程で往復が増える。

| 場面 | 入る工程 | 省くもの | 前提ブロック |
|---|---|---|---|
| 新しく書く | 工程1 | 短い文章なら工程5・6 を頭の中で | 付ける |
| 他人の下書きを書き直す・分かりやすくする | 工程1 | なし | 付ける |
| 自分の前の版を書き直す | 工程1 | 前の版の本文を開くこと | 付ける |
| 書き上げた文章を推敲する・確認する | 推敲 | 工程6・7 | 付ける |
| 定型文書の skill が中身を組んだあと | 工程1（一行）の後に工程6・7、推敲は文と事実のパス | 工程2〜5（型の skill が決めた見出し・必須セクションは変えない） | 付けず、型の skill の出力形式に従う |
| AI が繰り返し読む指示の文を整える | 工程7 だけ | それ以外すべて（中身と構造は instruction-design） | 付けない |

**他人の下書きは素材の一部として扱う。** 工程3 でそこから主張と事実を抜き出してから三つに分ける。
抜き出す前に構造だけ直すと、元にしかない事実が落ち、元の読者に向けた組み立てが残る。

**自分の前の版は開かずに工程1 から書く。** 開いて差分で直すと、前の版の構造がそのまま残り、やり直した
ことにならない。工程ファイルに「前の版からの差分」と書いてしまったら、やり直していない証拠なので
工程1 へ戻る。

**推敲から入るときは、先に工程1〜5 の最小版を工程ファイルに書き起こす。** 推敲の各パスは、読者の予算
（工程1）・目的（工程2）・素材の三分類（工程3）・中心文（工程4）・各節の一文（工程5）と突き合わせる
ので、これがないと検査の相手がない。一行ずつでよい。下書きの本文からではなく、依頼と素材から起こす。
本文から起こすと、逆アウトラインの突き合わせが本文どうしの比較になり、意図とのずれが出ない。
素材が下書きしかなければ、推定したことを前提ブロックに書く。

## 工程と参照ファイル

**工程に入る前に、その工程の参照ファイルを読む。** 全体像だけで書き始めない。

| 工程 | アウトプット | 読むファイル |
|---|---|---|
| 1 読者 | 読者の一行。役割・前提知識・関心・読む量の予算 | `references/stages-1-4.md` |
| 2 目的 | 目的の一文と、六つの種類のうちどれか | 同上 |
| 3 素材 | 素材の三分類。既知・知るべき未知・知らなくてよい | 同上 |
| 4 文意 | 中心文の一文と、支える主張（三つまで） | 同上 |
| 5 構造 | 見出しと各節の一文までのアウトライン、認知フレームを作る先頭の一文 | `references/stage-5.md` |
| 6 節 | アウトラインの各節が埋まった本文 | `references/stages-6-7.md` |
| 7 文 | そのまま渡せる状態の全文 | 同上 |
| 推敲 | 理解・構造・文・事実の四つのパスを通した完成稿 | `references/revision.md` |

各工程の出口条件は参照ファイルの末尾にある。

## 出力

素材から確実に言えない箇所には、ラベル付き角括弧プレースホルダを置く。散文で濁さない。
`[日付A: 相手チームの提案日]` `[金額: 見積もり待ち]` `[要確認: この数値は素材に根拠なし]`

発信も検証も筆者の責任なので、どこを確かめるべきか分からない下書きを渡さない。

**確認事項には、推敲で作った対応表のうち「素材にない」「素材より強い」と判定された行も載せる。**
プレースホルダは、書いている最中に自分で気づけたものしか拾えない。気づかずに書いた断定は本文の
体裁に紛れるので、対応表でしか出てこない。

**工程1〜5 のアウトプットを本文の前に置く。** 読者・目的・落としたもの・中心文・各節の一文の
五つは、本文を読んでも外れているかどうか分からない。本文には書かれたものしかないので、筆者が
意図した筋と一致しているかは本文からは出てこない。先に渡せば筆者が一行で訂正でき、質問を増やさずに
誤った前提での生成を防げる。**後ろに置くと、外れた前提のまま本文を読ませることになる**（性質1）。
見出しの階層と工程6・7 は本文そのものに現れるので添えない。プロジェクトやユーザーの規約が
並び（確認事項を冒頭に置く等）を指定していれば、それに従う。

**前提と確認事項の合計が本文を超えたら畳む。** 短い連絡ほど、確かめる材料のほうが本文より重くなる。
そうなると筆者は前提を読まずに本文だけを見るので、先に置いた意味が消える（性質3）。三つとも空白を
除いてコマンドで数え、超えていたら次の順で落とす。

1. **各節の一文** — 節が一つなら書かない
2. **落としたもの・後ろへ回したもの** — 挨拶と内容のない前置きだけなら書かない。読者の判断を変えない
3. **確認事項の説明** — ラベル付きプレースホルダで何を入れるか分かるなら、項目名だけを並べる

読者・目的・中心文は畳んでも残す。一行ずつまで縮めてよいが、消すと本文が丸ごと外れていても
気づけない。

**畳む対象になる文章では、対応表で「素材にない」と判定された行を確認事項に上げず、本文から消す。**
本文が短いほど書き直しは一瞬で済むのに対し、残して確かめてもらうと、確認する量が本文を超える。
「素材より強い」行は、断定を弱めて本文に残す。畳まない文章では従来どおり確認事項に載せる。

**各工程で決めた時点のものをそのまま持ってくる。** 書き終えてから思い出して書くと、本文に合わせた
辻褄合わせになり、確かめる意味がなくなる。工程ファイルに追記したものをそのまま貼る。

```markdown
## この下書きの前提

- 読者（工程1）: <一行。役割・前提知識・関心・読む量の予算>
- 目的（工程2）: <読み終えた読者がどうなっているか>
- 落としたもの・後ろへ回したもの（工程3）: <名指し>
- 中心文（工程4）: <一文>
- 各節の一文（工程5）: <節ごとに一行>

（違っていれば指摘してください）

## 本文

（そのまま使える状態）

## 確認事項

- [日付A: ...] — 何を入れるか
- 「〇〇は△△である」— 素材に出どころなし。削るか、根拠を足すか
- 「大幅に改善する」— 素材は「改善が見込める」。断定を弱めるか、根拠を足すか
```

## 手直し

渡したあと、筆者から前提の訂正か確認事項の返答が戻ってくる。どちらも本文の手直しになるが、
**入り直す工程が違う。**

**前提を訂正されたら、その項目を決めた工程まで戻る。** 戻り先は前提ブロックの各項目に書いてある。
そこから下を作り直す。文だけ直すと、元の前提で組んだ構造がそのまま残る。

**確認事項の返答は、返ってきた中身で分ける。** プレースホルダが埋まるだけなら本文を置換する。
返ってきた事実が素材の仕分けや中心文を変えるなら、工程3 か工程4 まで戻る。

## 裏付け

四つの性質と各規則の裏付け、採用時に確認した限界は `references/evidence.md` にある。
規範を見直すときだけ読む。**書いた文章には出さない。**
