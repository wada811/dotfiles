## 工程5: 構造

**見出しと、各節が何を言う節かの一文まで作ってから書く。** 思いつきを並べるだけでは質が変わらず、
階層にして初めて効く。見出しは名詞句なので何の話かを特定するだけで、何を言う節かは言わない。一文まで
書くと、本文を書く前に筋を検査でき、推敲の逆アウトラインで突き合わせる相手にもなる。

1. **分量の予算を決める**。読者層の「読む量の予算」から節の数と節あたりの長さを逆算する。
   予算が小さいなら支える主張を減らす。**削るのは節であって文ではない**
2. **認知フレームを作る一文を先頭に置く**（下記）
3. **中心文をその直後に置く**。経緯・背景・検討過程は後ろへ回す（性質3）
4. **残すもののうち、必要なときだけ見ればよいものを末尾かリンクへ出す**。出典や詳細な経緯は
   本文の流れに入れない
5. **各節の一文を順に読んで筋が通るか確かめる**。通らないなら順序か粒度が間違っている

### 認知フレームを作る一文

**先頭の一文で、読者の認知フレームを作る。** この先を何の話として読むかが、ここで決まる。渡すのは
三つ。**何についての文章か、読者に何が求められるか、期限があればいつまでか。** 読者はこの三つから、
何を判断しながら読むかを決める。

**中心文とは別物。** この一文は読み方を指定し、中心文は内容を言う。

```
認知フレーム: 【相談】料金改定について、今週中に意見をください。
中心文:       値上げ幅は 10% が妥当だと考えています。
```

短い共有では、一文が両方を担うことがある（`【共有】新しい承認フローを来週から始めます。対応は
不要です。`）。そのときは同じことを二度書かない。

**読む前に与えたときだけ効果があり、読んだ後では効かない**（性質1: 予測の材料は先にしか効かない）。
末尾に「というわけで承認をお願いします」と書く構成は、そこに至るまで何を判断しながら読めばよいか
分からない状態を作る。

形は媒体で変える。Slack は角括弧ラベルと一文（`【相談】料金改定について、今週中に意見をください。`）、
文書は表題の直下に一文、メールは件名と冒頭一文。

種類のラベルが要るのは、読者に行動や判断が求められる文章だけ。説明や解説では表題と冒頭の一文で
対象と範囲が分かれば足りる（`Kotlin の coroutine のキャンセル処理について、実装で踏みやすい
落とし穴を書きます。`）。

**中身のない一文では認知フレームができない。**「本件について共有させていただきます」は、何を共有するのかを
渡していない。主題そのものを入れる（`【共有】新しい承認フローを来週から始めます。対応は不要です。`）。

### 見出し・箇条書き・強調

構造を目に見える形にすると切れ目を掴めるが、拾い読みを促す副作用がある。**見出しを増やすと拾える
話題は増え、各話題の中身の記憶は減る。** 深く理解してほしい文章では見出しを増やさない。

- **見出し**: 話題が三つ以上あるときだけ付ける。内容を特定できる具体的な句にする
- **箇条書き**: 並列の項目（選択肢・条件・関係者）に使う。因果や条件が絡む議論は文章で書く。
  箇条書きにすると項目間の論理関係が消える
- **番号付き**: 順序があるとき（手順・優先順位・時系列）に使う。順序がないものに番号を振ると、
  無い順序を読者が探す
- **入れ子**: 項目に従属する条件・例外があるときだけ。二段まで。三段目は別の節に分けるべき構造
- **数を宣言したら列挙にする**: 「やることは三つです」と書いて散文で続けると、読者は数えながら
  読むことになる。数を言うなら箇条書きにし、散文で書くなら数を言わない
- **強調**: 一つの節に一、二箇所まで。増やすほど一箇所あたりの効果が薄まる

### 工程5 の出口

**アウトプット**: 見出しと各節の一文までの階層アウトラインと、認知フレームを作る先頭の一文。

**次へ進む条件**

1. 冒頭の二文を抜き出して、認知フレームと中心文が別のことを言っているか
2. 各節の一文だけを順に読んで筋が通るか。見出しの句だけで済ませない
3. 総量を数えて、工程1 の予算に収まっているか。超えていたら節を削る
4. 頭の中で済ませる短い文章でないなら、ここで止めて前提とアウトラインを筆者に渡したか
