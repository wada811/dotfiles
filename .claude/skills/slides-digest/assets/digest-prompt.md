登壇資料を読んで、記事を書きます。

入力:

- 資料 PDF: {{PDF}}（全 {{PAGES}} ページ）
- タイトル: {{TITLE}}
- 資料の公開 URL: {{SLIDES_URL}}
{{CONTEXT_BLOCK}}

## 作業

{{READING_PLAN}}

そのうえで:

- **発表全体を通して登壇者が伝えたかったメッセージを 5〜8 個抽出する。**
  - メッセージ＝聞き手に持ち帰らせたい主張。スライドの見出しをそのまま使わない
  - スライド1枚に1メッセージではない。複数のスライドが1つのメッセージを構成することも、
    メッセージを持たないスライド（表紙・自己紹介・つなぎ）もある
  - **7個を超えたら統合する。** 節が多いほど主張はぼやける
- メッセージごとに1セクションを作り、`{{OUT}}` に Write する。

## 出力フォーマット

冒頭はタイトルの H1 行と、その次に1行:

```
<登壇者名> / [資料]({{SLIDES_URL}})
```

登壇者名は自己紹介スライドから取る。**リンク先はローカルの PDF パスではなく上の公開 URL**。

続けて:

```
## この発表の主張

- 発表全体の主張を箇条書き3つで。ここだけ読めば何の発表か分かるように
```

以降、メッセージごとに:

```
## <メッセージを一文で言い切った見出し>

![p.12](https://files.speakerdeck.com/presentations/{{SLIDES_ID}}/slide_11.jpg)

- （0〜3個）
```

- 画像はそのメッセージを裏づけるスライドを 1〜3 枚。裏づけにならない画像は貼らない
- 箇条書きは **0〜3 個**。書くことがなければ画像だけで構わない

### 表現の選び方

箇条書きに限らない。**内容が一番速く正確に伝わる形を選ぶ**。

- **表** — 資料が対応関係や内訳を列挙しているとき（「問題 A にはこの部品」の対応表、
  「この分類が何件」の内訳、API 名や設定値の一覧）。箇条書きの上限は表には適用しない。
  読者がこれを参照するために資料を開き直すことになるなら、載せる価値がある。
  ただし表にするのは**資料が実際に列挙しているもの**だけで、自分で分類を作らない
- **図**（mermaid のコードブロック）— 段階・分岐・依存関係のように、
  文字を追うより形で見たほうが速いとき
- **コードブロック** — API 名・設定値・コマンドなど、正確さがそのまま価値になるとき
- **引用** — 資料の言い回しをそのまま残したいとき

資料が全体の対応関係や内訳を示している場合は、その手前に参照用の節を置く（任意）:

```
## 早見表

| 問題 | 対応する部品 |
| --- | --- |
```

**この節はメッセージの節数に数えない。** メッセージの中に収まりきらない対応表は
ここにまとめる。資料が全体像として示していないなら、この節は作らない。

最後に:

```
## 持ち帰れること

- 箇条書き3〜5個。読者が自分の仕事に当てはめられる形で
```

{{EXTRA_SECTIONS}}

## 厳守事項

- 画像 URL の数字は **ページ番号から1引いた値**（p.12 なら `slide_11.jpg`）。
  `slide_0.jpg` が1ページ目にあたる。総ページ数は {{PAGES}} なので、
  `slide_{{PAGES}}.jpg` 以上は存在しない。
- **画像の説明を書かない。** レイアウトや図形の描写（「左に◯◯、右に△△を並べた図」
  「円環図」「2×2のマトリクス」など）は一切禁止。スライドの文言の書き写しも不要。
  判断基準: **その箇条書きを消しても、画像を見れば同じことが分かるなら、その箇条書きは不要。**
  箇条書きに書いてよいのは画像から読み取れないことだけ — 前提・出典・
  画像では字が小さくて読めない数字や固有名詞・前のメッセージとのつながり・実務での意味。
- **長い散文を書かない。** 読みづらいのは長文であって、箇条書き以外が悪いのではない。
  段落で説明したくなったら、表・図・箇条書きのどれかに置き換えられないか先に考える。
  地の文が要るときも2〜3行までにする。
- **読み手は「その分野の隣にいる人」を想定する。** Android の資料なら iOS エンジニアや
  PM、SRE の資料ならアプリ開発者、デザインの資料なら開発者。関心はあるが中にはいない人。
  この人が読んで詰まる語だけ補足する。
  - その分野の基礎語には補足を付けない（Android の資料での Compose、SRE の資料での SLI）。
    隣にいる人なら名前は知っているので、注釈はくどくなるだけ
  - 分野をまたぐ語・略語・社内語・その分野でも一般的でない語には、初出時に
    「（＝〜のこと）」と一言添える。カタカナで済ませない
- 1つの箇条書きは2行以内（表の行はこの制限の対象外）。
- スライドに書かれていないことを推測で書かない。
- **中立にまとめる。** 読み手の状況への当てはめ、「あなたの場合はこうすべき」という提案、
  自分の意見や評価は書かない。書くのは資料が言っていることだけ。
  どう使うかは読んだ人が決める。
- 最後に `DONE {{OUT}}` とだけ出力する。
