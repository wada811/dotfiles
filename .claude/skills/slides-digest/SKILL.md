# slides-digest スキル

登壇資料を「読めば発表が分かる記事」にする。資料そのものを開かなくても、
何を言っていた発表なのかが分かる状態がゴール。

## このスキルが解こうとしている問題

資料まとめは放っておくと**スライドの説明**になる。「左に現状、右に理想を並べた図」
「3つの円が重なる図」——これは画像の隣に画像の説明が並んでいるだけで、読者にとっては
資料そのものを見るのと変わらない。価値があるのは、**資料全体を通して登壇者が
何を言いたかったか**を抜き出すこと。スライド1枚1枚には主張が載っていないことも多く、
複数枚がまとまって初めて1つの主張になる。だからこのスキルは
「スライド単位」ではなく「メッセージ単位」で記事を組み立てる。

## 手順

### 1. 資料を特定する

URL があればそれを使う。タイトルや登壇者名しか分からないときは検索する。

```bash
python3 <skill>/scripts/slides-search.py "<セッションタイトル>" "<イベント名>"
```

同名の資料が複数出ることがあるので、ヒットしたタイトルをユーザーに確認できる形で示す。

### 2. PDF と slides_id を取る

```bash
python3 <skill>/scripts/slides-fetch.py "<slides_url>" --out-dir tmp/slides --key <短い名前>
```

JSON で `slides_id` / `pdf` / `pages` / `title` / `description` が返る。この3つが後で要る。

- `slides_id` — スライド画像の URL に埋める 32 桁の16進
- `pages` — 画像番号が範囲内かの検証に使う
- `pdf` — 中身を読む対象

**ローカルの PDF を渡された場合**は 1〜2 を飛ばす。ただし slides_id が無いので
スライド画像 URL は作れない。その場合は画像なしの記事にするか、
`pdftoppm -jpeg` でページを画像化してローカル参照にするかをユーザーに確認する。

### 3. 記事を書かせる

```bash
python3 <skill>/scripts/slides-digest.py \
  --pdf tmp/slides/<key>.pdf --slides-id <slides_id> --pages <pages> \
  --title "<タイトル>" --slides-url "<slides_url>" --out tmp/digest/<key>.md
```

自分で PDF を読まずにサブプロセスに投げるのは、資料が数十ページあるため。全ページを
自分のコンテキストに載せると数本読んだだけで圧迫され、本来やるべき検証や複数資料の
突き合わせができなくなる。記事本文も同じ理由で、読むのは検証のときだけにする。

**ただしサブプロセスにしても使用量の枠は減らない。** 枠はアカウント共有なので、
節約できるのはコンテキストだけ。実際に効くのは**画像として読むページ数を減らすこと**で、
使用量はほぼそれに比例する。129 ページの資料を全ページ画像で読ませて枠を使い切った実測がある。

`slides-digest.py` は自動で読み方を切り替える。`pdftotext` の抽出量が
1ページあたり 60 字以上なら、テキストを「目次」として渡し、画像で読むのは
裏づけスライドだけに絞る（既定の上限 30 ページ、`--max-visual-pages` で変更可）。
抽出できない完全画像 PDF のときだけ全ページを画像で読む。
起動時にどちらを選んだか表示されるので確認すること。

**複数本を処理するとき**、30 ページ以下の資料なら同時に走らせてよい。それより長い資料は
1本ずつ流す。同時に走らせると枠を食い合い、途中で全部止まる。

補助資料（イベントの実況、登壇者の補足ブログなど）がある場合は `--context <path>` で渡す。
「会場の反応」のような節を足したい場合は `--extra-sections` に指示文を渡す。

### 4. 検証する

```bash
python3 <skill>/scripts/digest-verify.py tmp/digest/<key>.md --pages <pages> --slides-id <slides_id>
```

見ているのは、目で気づきにくく読者には確実に見える壊れ方:

- スライド画像の番号が範囲外（別のスライドが出るか、画像が壊れる）
- 画像の描写が残っている（「左に◯◯」「円環図」など）
- 散文の段落が混ざっている
- メッセージの節が 5〜8 から外れている

問題が出たら該当箇所を直す。全部書き直す必要はない。

### 5. 出力先に置く

ユーザーが行き先を指定していればそこへ。Notion に載せるなら `notion-article` スキル、
`learnings/` に残すなら front-matter の処遇を付けて保存する。

## 記事の形

```markdown
# <タイトル>

<登壇者> / [資料](<slides_url>)

## この発表の主張

- 全体の主張を3つ。ここだけ読めば何の発表か分かるように

## <メッセージを一文で言い切った見出し>

![p.12](https://files.speakerdeck.com/presentations/<slides_id>/slide_11.jpg)

- 画像から読み取れないことだけ、0〜3個

（メッセージの数だけ繰り返す。5〜8 個が目安）

## 持ち帰れること

- 読者が自分の仕事に当てはめられる形で3〜5個
```

見出しは名詞句ではなく**言い切りの文**にする。「エラーバジェットについて」ではなく
「エラーバジェットは残高ではなく交渉材料として使う」。名詞句だと目次を読んでも
何を言っていたのか分からない。

## 判断に迷ったときの基準

**その箇条書きを消しても、画像を見れば同じことが分かるなら、その箇条書きは不要。**

書いてよいのは画像から読み取れないことだけ:

- 前提（どういう組織・規模の話か）
- 出典（引用元の書籍・論文・他社事例）
- 画像では字が小さくて読めない数字や固有名詞
- 前のメッセージとのつながり
- 実務で何を意味するか

書くことがなければ画像だけで構わない。空欄を埋めるために説明を足さない。

## 既知の落とし穴

- **`pdftotext` の結果を記事の唯一の根拠にしない。** 実測（20 本）では 18 本で
  テキストが取れたが、**図の中の文字は画像なので抜ける**。
  「使われる = 気づける × 使える × 完了できる」が「3 | = × ×」になった実例がある。
  テキストは話の流れをつかむ目次として使い、数字・図・強調は必ず画像で確認する。
  完全画像 PDF（実測 20 本中 2 本）はテキストが 0 なので全ページ画像で読むしかない。
- **スライド画像の番号はページ番号 − 1。** `slide_0.jpg` が1ページ目。
  ここがずれると全ての画像が1枚分ずれるが、記事を読まないと気づけない。
- **PDF ダウンロードを無効にしている資料がある。** その場合 `slides-fetch.py` は
  PDF リンクなしで終わる。画像 URL は slides_id から作れるので、
  スライド画像を1枚ずつ読ませる経路に切り替えるか、ユーザーに伝えて判断を仰ぐ。
- **サブプロセスは書かずに「できた」と報告することがある。** 完了判定は
  ファイルの実在とサイズで行う（`slides-digest.py` は既にそうしている）。
  失敗時はログの末尾が表示されるので、枠切れなのか別の失敗なのかをそこで見分ける。
- **メッセージが 8 個を超えがち。** `digest-verify.py` で引っかかったら、
  近い主張どうしを 1 節に統合する。節が多いほど何を言いたい発表だったかがぼやける。
- **作り直すと指示に書かなかった節が静かに消える。** 既存記事を別形式に作り直すときは
  `digest-verify.py --compare <旧版>` で見出しを突き合わせる。

## 関連スキル

- `google-slides-fetch` — Google スライド専用。Speaker Deck ではなくそちらの URL ならこれ
- `notion-article` — 書き上がった markdown を Notion の記事ページ DB に載せる
- `link-insight` — 記事 URL 一般から仕事への活用アイデアを出す。資料の内容理解が目的ならこちら
