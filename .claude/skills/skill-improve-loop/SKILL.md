# skill-improve-loop — 回して、結果から直す

対象の skill を実際の仕事で回し、つまずいたところから直す。直したものを次の数件で試し、
効いたかを確かめる。目的は、こなした件数ではなく、**人が見なくても正しく動く skill** に
近づけること。

この skill は原則だけを持つ。何を回すか・結果をどこに書くか・1 周を何件にするか・いつ止まるかは、
呼び出し側の skill（以下、ループの skill）が決める。

## 問題への向き合い方（中心）

結果に問題が出たら、その場で手順を書き足して終わりにしない。粘り強く、角度を変えて問い続ける。

- **何が問題か**: 結果（出力・ログ・差分）から、実際に起きたことを具体的に言う。
  「うまくいかなかった」ではなく「ボタンの文字が 2px 下にずれた」
- **なぜ問題か**: それで何が困るのか（結果が誤る・回数が増える・人の確認が要る）。
  困らないなら問題ではない。直さずに許容し、理由を書く
- **なぜ起きたか**: 手順に書いていなかったのか、書いてあるのに守れなかったのか、道具の不足か、
  対象の本質的な性質か、比べる基準の誤りか。1 件の観察で決めつけず、他の件でも起きているかを見る
- **解決できる方法はないか**: 手順を書き足す・道具を直す・対象の分け方を変える・許容値を置く・
  人の判断に回す。1 つの方法で解けなければ別の方法を考える。「無理」と言う前に、
  他の角度（公式ドキュメント・ライブラリのソース・先行事例）を当たる
- 直したら、**次の数件で効いたかを確かめる**。効かなければ、原因の見立てを疑い直す

## 回し方

- **直すのは 1 件ごと**: 周の終わりまで待たない。道具や基準の不足は、気づいた時点で直せば
  残りの件すべてに効く
- **直したら、前の結果を壊していないか確かめる**: 道具や基準を直したら、それまでの結果を
  取り直して比べる。変わったら、どちらが正しいかを確かめる。振る舞いを変えないつもりの整理でも省かない
- **周の終わりに、次の周と比べる数字を決めて書く**: 件ごとの試行回数・効いた修正の回数・
  合否など。数字を決めておかないと、次の周で効き目を判断できない
- **対象を散らす**: 最初の周は似た件でそろえて仕組みを 1 つで済ませてよい。2 周目からは種類・
  大きさ・置き場所を散らす。易しい件ばかりだと、手順が効いたのか対象が易しかったのかを分けられない
- **こなれてきたら初期の件を回し直す**: 新しい種類の問題が出なくなってきたら、初期の件を今の
  手順でもう一度回す。初期の件は、直る前の手順や基準のもとで合格にしているため
- **重い作業はサブエージェントに出す**: 1 件の実行、原因を掘るためのコード読み、結果の取り直しと
  比較。結果は要約（分かったこと・根拠のファイルや数値・残った問題）で返させる。どう直すかを
  決めるのは親

## 確かめ方

- **サブエージェントの「合格」を鵜呑みにしない**: 成果物そのもの（画像・出力・差分）を自分で見る
- **道具の数字を信じる前に**: 合否を決める数字は、使い始めと道具を直したときに一度、別の方法
  （自分で見る・別のコマンドで数える）と食い違わないかを確かめる。数え方の誤りで合否の数字が
  ずっと小さく出ていたのに、1 周気づかなかった例がある
- **確かめは独立な方法で**: 同じ前提を共有する 2 つを比べても確かめにならない（同じ欠陥を持つ
  2 つは一致する）。本番の実物・本番の経路・ソースを読むこと、のように前提を共有しない方法を
  使う。それができないときは「未確認」と書き、結論を決めつけない
- 確かめていないことを、確かめたように書かない。効果は次の周の数字で確かめてから書く

## 人の判断が要る問題（1 way door と 2 way door）

取り返しのつかないもの以外は、試しにやってみる。

- **止まる（1 way door）**: 取り返しがつかないもの、人の名義で他の人に見えるもの（PR・issue・
  コメント・チャットへの投稿、本番のデータの書き換え）。操作はせず下書きを作って呼び出し元に渡し、
  その操作を待たずに続けられる限り続ける
- **試してみる（2 way door）**: 作業ツリーの中だけで、あとで戻せるもの（手順・道具・基準の
  取り方・対象の分け方を変える）。まずやってみて、結果と一緒に報告する。決めるのが人であっても、
  試した結果があれば判断が軽くなる
- プロダクトの判断（仕様として正しいのはどちらか）は、今の本番どおりにして先へ進み、周の終わりの
  集計に「人の判断が要ること」として書く

## 直す側の skill 自身も直す

ループの skill にも、上の「問題への向き合い方」をそのまま当てはめる。直す段を一段ずつ積み上げる
ことはできないので、この原則を、どの段にも当てはまるものとして扱う。原則そのもの（この skill）を
直すのは Andy。

- **見直す合図**: 次のどれかが起きたら、続きを回す前にループの skill を見直す
  - 周が終わった（この周の流れに無駄・抜けがなかったか）
  - 書いてある流れどおりに進められなかった、または流れから外れて進めていた
  - 人に進め方を問われた・指摘された（外からの見直し）
- **直し方**: 書いてあることと実際の何がずれたか、次に読む者が何を誤るか、なぜずれたか、を問う。
  流れを実態に合わせるのか実態を流れに戻すのかは、どちらが目的に近いかで決める
- 実際の進め方と書いてある流れを、ずれたままにしない（次に読む者は書いてあるほうを信じるため）

## 改善の記録

何をなぜ直したかを、直した skill のディレクトリの記録ファイル（`improvements.md` など、ループの
skill が決める）に、根拠と一緒に書く。新しいものを下に足す。

- 根拠は「どの件で何が起きたか」。思いつきの直しと区別できるようにする
- 対象の skill への直しと、ループの skill 自身への直しは、別のファイルに分ける
- 直しと記録は同じコミットにする
