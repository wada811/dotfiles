# commit — 意図単位のコミット

「1コミット = 1意図」を保証する。目的が同じ変更は複数ファイルにまたがっていても1つにまとめ、目的が違う変更は同じファイル内でも分ける。

## Step 1: 現状確認

```bash
git status
git diff --staged
git diff
git remote -v
git log -20 --format='%s'
```

`git log` は**メッセージの様式を既存ログに合わせるため**に見る（Step 4）。ステージ済みの変更がない場合は何をステージするかを確認する。

## Step 2: 意図の分析

差分全体を読み、変更を「意図」の単位でグルーピングする。分類の目安は、新しい振る舞いの追加（feat）・バグ修正（fix）・振る舞いを変えない整理（refactor）・テスト（test）・ドキュメント（docs）・ビルド設定や依存（chore）。

**単一意図** → Step 4 へ。**複数の意図が混在** → Step 3 へ。

## Step 3: 分割提案

分割案を提示してユーザーの確認を得る。各コミットの要約と対象ファイルを並べ、この順番でよいかを聞く。承認後、意図ごとに Step 4 を繰り返す。

## Step 4: コミット

### メッセージは日本語で書く

**既定は日本語。** リポジトリの既存ログが英語で統一されている場合（チームのプロダクトリポジトリなど）は、そのリポジトリの CLAUDE.md の指示に従う。指示がなければ `git log -20 --format='%s'` で既存ログを見て判断する。Conventional Commits の prefix を付けるかどうかも既存ログに合わせる。

長さは**文字数でなく表示幅**（全角を 2 桁と数える）で測る。日本語で「50 文字」と数えると表示幅 100 桁になり、`git log --oneline` の表示が崩れるうえ制限として働かない。

- **タイトルは表示幅 50 桁以内**（日本語なら 25〜30 文字が目安）。超えるなら動詞や修飾語を削る。**内容が二つ入っているなら、短縮ではなくコミットを分ける**
- **本文は表示幅 72 桁で折り返す**（日本語なら 35 文字前後）。説明が必要なら空行を挟んで本文に書き、What ではなく Why を書く

迷ったら実測する。

```bash
python3 -c "import sys,unicodedata as u; s=sys.argv[1]; print(sum(2 if u.east_asian_width(c) in 'WF' else 1 for c in s))" "<タイトル案>"
```

### 本文はファイル経由で渡す

複数行の本文や、バッククォート・記号を含む本文は、ファイルに書いてから渡す。

```bash
git commit -F tmp/commit-msg.txt -- <対象パス>
```

- `-m` の複数指定・`$()`・heredoc をコミットコマンドの中で使わない。シェルがコマンド置換として展開したり、権限の確認が挟まったりする
- 一時ファイルの置き場所はプロジェクトの規約に従う（多くは作業ツリー内の `tmp/`）。OS の `/tmp` は避ける
- 一時ファイルには前回の内容が残っているため、書き込む前に読む

### 並行セッションの変更を巻き込まない

他のセッションやジョブが同じ作業ツリーを触っていることがある。`git add` の後、`git commit -F <msg> -- <パス>` の形で**対象パスを明示**し、自分が作った変更だけをコミットする。巻き込んだら次のコミットで戻す。

ただし同一ファイルを複数のコミットに分割するときは、パス指定が index の内容を無視してしまうため使わない。

### Co-Authored-By

いま動いているモデル名を書く。特定のモデル名を skill やテンプレートに固定すると、書き手が変わったときに実際と食い違う。迷ったら `git log -20 --format=%B | grep Co-Authored-By` で直近の表記を確認する。

### コミット前の処理

フォーマッタや生成物の更新など、コミット前に走らせる処理がプロジェクトにある場合は、その CLAUDE.md の指示に従う。差分が生じたら `git add` して同じコミットに含める。

## Step 5: push

**push は外部公開で、取り消せない。**

1. `git remote -v` で remote の有無を確認する。remote がなければ push しない
2. remote がある場合、**公開リポジトリや共有リポジトリへの push はユーザーに確認してから**行う。指示が明示されているか、そのセッションで恒久的に許可されている場合だけ自動で実行する
3. force push はしない。間違いは次のコミットで直す

## 完了後

コミットしたハッシュと要約を報告する。push していない場合は、していないことと理由（remote なし・確認待ち）を明示する。
