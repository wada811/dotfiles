# decision-distill — 判断のしかたを蒸留する

人が agent に仕事を任せると、agent の判断を人が訂正する場面が繰り返し起きる。その訂正には、人の判断のしかたが言葉になって現れている。この skill は、訂正や選択の記録からその人の判断の原則を取り出し、原則を使って判断するエージェントチームを作って、人が作業の詰まる一点（SPoF）にならない状態に近づける。

取り出した原則が本当に効くかは、原則を作るのに使わなかった判断で確かめて初めて分かる。この skill の手順の大半は、その確かめを意味のあるものにするためにある。

## 成果物

作業するプロジェクトの中に、一つのディレクトリを作って置く（例: `docs/decision-distillation/`）。

| ファイル | 中身 |
|---|---|
| `requirements.md` | 目的・材料と領域・チームが代わりに決めてよい範囲・検証の方法 |
| `design.md` | 工程・答えが混ざらないようにする工夫・検証の方法と結果の要約 |
| `decision-log.md` | 判断の時系列。人の発言は原文のまま、誰が判断したか（人か agent か）を書く |
| `points/` | 取り出し用の分岐点。別の観点の agent が見つけた見落としの一覧 |
| `validation/` | 検証用の状況（チームに渡す）と答え（判定にだけ使う）、回答、判定、結果 |
| `principles/principles.md` | 原則・候補・原則どうしの衝突・改訂の記録 |
| `team/team.md` | 役割・相互作用・決めてよい範囲と、それぞれの根拠 |

チームの役割の指示（agent と進行役の skill）は、原則集がプロジェクトの固有名や人に固有の判断を含むなら、そのプロジェクトに置く。

## 判断の基準

### 材料

- 一次資料は「分岐点」、つまり人が agent の判断を訂正した・選択肢から選んだ・新しい方針を示した・事実を教えた箇所とする。人の判断のしかたが言葉になって現れるのはそこだけだから
- agent の推奨どおりに人が選んだ分岐点は、根拠として弱いと明記する。人が提案を承認しただけかもしれないため。逆に、選択肢にない答えは重く扱う
- 一つのやり取りだけを材料にすると、その案件に特有の判断を原則と取り違える。memory の過去の訂正など、別の案件の記録と突き合わせる
- 別の観点の agent（レビュー・予行）が見つけた見落としも集める。人の判断ではないが、チームの役割を設計する根拠になる

### 検証用を先に取り分ける

- 原則を取り出す前に、分岐点の一部を検証用に取り分ける。取り出しに使った分岐点で確かめても、覚えた答えを返しているだけかどうかを区別できないため
- 分岐の種類ごとに取り分け、訂正を多めにする。訂正は agent が人と違う判断をした箇所で、再現できるかを最もよく試せるため
- 検証用の状況（訂正される前の状況）と答え（人の実際の判断と、判定で見るべき点）は別のファイルに書く
- 取り出し用の一覧を書いたら、検証用の答えが場面の説明などに漏れていないかを見直す。漏れは実際に起きやすい

### 答えを知る者に取り出させない

- すべての判断を知っている agent（材料を集めたセッション）は、原則を取り出さない。取り出し用の一覧だけを渡した新しい agent に任せ、検証用のファイルと元の記録を読まないよう指示する
- 原則を確かめるのは、取り出した agent とは別の agent にする。確かめ役は、根拠の水増し（人の判断でないものを数える）・帰属の誤り（agent が選んだ方法を人が求めたことにする）・根拠を超えた一般化を見つける。確かめの結果による改訂も、取り出した agent に戻す
- 独立した根拠が 1 件しかないものは、原則ではなく候補にとどめる
- 原則どうしがぶつかり、根拠から優先順位を決められないときは、人に聞く。答えは新しい分岐点として材料に加える

### チームを作る

- 役割は、実際に別々の見落としを見つけた観点から作る。根拠を書けない役割は入れない
- 確かめ役は、見落としを見つける一方で、厳しすぎる判断もする。指摘を原則で絞る判断役を置く
- 役割の指示には原則の中身を書き写さず、原則集を参照させる。書き写すと、原則が変わったときに食い違うため
- 決めてよい範囲は、one way door / two way door の原則で決める。引き返せる判断は、原則に当てはまらなくても解釈と根拠を明示して進める。引き返せない判断（取り消せない・外部に公開される・実在の人に届く・費用が発生する）と、原則どうしがぶつかって結果が大きく変わる判断だけを人に戻す。「原則から導ける判断だけを決めてよい」とすると、チームが人に戻しすぎ、人が SPoF のまま残る

### 検証する

- 原則も役割も持たない比較対象に、同じ状況を解かせる。チームが人と一致しても、比較対象も同じ判断をするなら、原則の効果とは言えないため
- 判定は別の agent に任せ、どちらがチームの回答かを伏せる。原則の番号や、チームの指示に固有の言葉を取り除き、どちらを先に並べるかは乱数で決める。伏せきれない違い（文体や長さ）は、結果の限界として書く
- 一度結果を見た検証用の分岐点は、改善の効果の検証に使わない。同じ分岐点で測ると、答えに合わせて直したのか判断のしかたが良くなったのかを区別できないため。次の検証の材料は、これから先のやり取りから、原則やチームを直す前に取り分ける
- 合格の基準は、結果を見て人が決める

## 更新するとき

チームが人に戻した判断と人の答え、チームが引き返せる判断で明示した解釈は、新しい分岐点として `points/` に加える。一定の数がたまったら、検証用を先に取り分けてから、取り出し担当の agent に原則集を改訂させ、検証をやり直す。

## 境界

- 材料に社外の個人の情報（氏名・連絡先など）が含まれる場合は、分岐点に書き写さない
- この skill を公開の場所に置くときは、組織や案件の固有名を書かない。原則集はプロジェクトの中に置く
- 原則集とチームを外部に公開すること、別のリポジトリへ push することは、人の確認を得てから行う

## 完了の条件

- 検証の結果（一致の件数・比較対象との差・限界）が `validation/result.md` にあり、人が合否を決めて `decision-log.md` に記録されている
- 人が決めたことと agent が決めたことが、`decision-log.md` で区別できる
