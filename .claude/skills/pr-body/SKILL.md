# pr-body — 保証だけを書いた PR 本文を作る・更新する

PR 本文の仕事は、diff からは分からない「なぜ・何を保証するか・何をやらないか・どこが不安か」をレビュアーに渡すこと。何をどう書き換えたか（how）は diff が示すので、本文には書かない。how を書いた本文はリファクタのたびに嘘になる。

## 引数

- PR番号（`#42` / `42`）または PR の URL → その PR の本文を**更新**する
- `--repo owner/name` → 対象リポジトリを指定する
- 省略 → 下の順で対象を決める

URL（`https://github.com/<owner>/<repo>/pull/<番号>`）が渡された場合は owner / repo / 番号をそこから抽出する。リポジトリの既定をプロジェクト側の CLAUDE.md で定めている場合はそれに従う。

## Step 0: 対象とモードを決める

次の順で対象を決める。1〜3 で PR が決まれば**更新**、4 なら**新規**。

1. **引数**: PR番号または URL が指定されていればそれを使う
2. **会話コンテキスト**: 引数がなければ、このセッションで直前に扱っていた PR の番号を対象にする（直前に作成・確認・対応していた PR、ユーザーが会話中に挙げた番号など）。対象を決めたら「コンテキストから #42 を対象にした」と一行で明示し、取り違えていればユーザーがすぐ指摘できるようにする
3. **現在のブランチ**: 引数もコンテキストもなければブランチの PR を探す

```bash
gh pr view --json number,title,url,headRefName 2>/dev/null
```

4. **新規**: ブランチに PR がなければ、そのブランチから作る PR の本文を作る（PR は作らない）。ただし現在のブランチが base・既定ブランチ（`main` / `master` やプロジェクトの CLAUDE.md が決める base ブランチ）のときは新規にせず、自分の open PR を一覧してユーザーに確認する

```bash
gh pr list --author @me --state open --limit 30
```

stack PR のように open PR が多いリポジトリでは `--limit 10` だと目的の PR が漏れるため、`--limit 30` を使う。

## Step 1: 素材を集める

```bash
# 新規・更新共通: base と差分
gh pr view <番号> --json baseRefName,headRefName,title,body,url   # 更新時
git log <base>...HEAD --oneline
git diff <base>...HEAD --stat
git diff <base>...HEAD
```

- base は PR の baseRefName。新規ならプロジェクトの規約（CLAUDE.md）が決める base ブランチを使う
- 背景の素材として、ブランチ名やコミットに出てくる issue・会話中に出たリンク（チャット・ドキュメント等）を読む。背景をでっち上げない。素材がなければ `[背景: 〜を記入]` のラベル付きプレースホルダを残す
- テンプレートは `.github/pull_request_template.md`・`.github/PULL_REQUEST_TEMPLATE/*.md`・`docs/pull_request_template.md` の順に探す。なければ Step 2 の 4 つの役割の名前（背景 / 変更内容 / スコープ外 / 見てほしい点）を見出しにして書く

## Step 2: 本文を書く

### テンプレートの扱い

- 見出しの名前と順序はテンプレートのまま使う
- HTML コメント（`<!-- -->`）はテンプレートの記入説明なので消す。ただし先頭の stacked PR 注記など、人が書いたコメントは残す
- チェックボックスの節（優先度・確認項目等）は、判断材料があればチェックを入れ、なければ未チェックのまま残して最終報告で埋める項目として挙げる
- 「該当しない場合はこの節を削除」と説明にある節は、該当しなければ削除する。それ以外で書くことがない節は「該当なし」と書く（節ごと消すとテンプレートの確認項目が落ちる）

### 節の役割

規則は見出しの名前ではなく、節の役割に当てる。テンプレートの見出しと記入説明を読み、各節が次のどの役割に当たるかを先に決める。

| 役割 | 渡すもの | 見出しの例 |
|---|---|---|
| 背景 | この PR が要る理由 | 背景 / Why / Motivation / 課題 |
| 変更内容 | PR が保証すること | 対応したこと / Summary / Changes / What |
| スコープ外 | やらないことと、その理由 | 対応しないこと / Out of scope / Non-goals |
| 見てほしい点 | 自信のない点 | レビューポイント / Notes for reviewers / Review focus |

- どの役割にも当たらない節（優先度・スクリーンショット・確認項目等）は、上の「テンプレートの扱い」だけに従う
- テンプレートに役割の節がなくても、節は足さない。その役割の内容は、書き手が一番近いと判断した節に置く

### 中身の規則

1. **変更内容には、PR が保証することだけを書く**
   - 保証とは、コードの外から観測できる振る舞いや性質のこと。ユーザー・呼び出し側・ビルド・CI のどれかから見えるものを主語にする
   - 判定: 「この項目は、同じ保証のままコードをリファクタしても真のままか」。偽になる項目は how を書いている
   - 関数名・引数・型名・エラー文言が主語や目的語になっている項目は、観測できる結果の言い方に直すか削る
   - 保証を変えない変更（集合・順序・挙動が変わらない等）はその事実を 1 項目で書く。レビュアーが一番確かめたい点だから
2. **1 項目 1 文。1 行で読み切れる長さにする**（目安: 表示幅 80 桁 = 全角 40 字前後）
   - 目安の理由は、GitHub の web 表示で折り返しが増えると読みにくいため。厳密な上限ではない
   - 超えたら、分けても意味と文の自然さが保てるときだけ分ける。分けると理由が切れる・文が不自然になるなら、多少超えても残す
   - ひと続きの文章は読まれない。長くなったら、主張を親の行に、理由・例・条件を子の行に分ける（入れ子は二段まで）
   - 1 文に「〜し、〜して、〜ため」と意図を重ねない
   - 節の結論になる 1 項目だけを太字にしてよい
3. **理由（why）を書く**。背景にはこの PR が要る理由を書く。設計の選択には「〜のため」を 1 項目添える。却下した案があれば「〜にしなかったのは〜のため」と書く
4. **スコープ外には、レビュアーが「なぜないのか」と思うものを理由付きで書く**。後続 PR で入れるものは「後続の PR で入れる」と書く
5. **見てほしい点には、自信のない点を書く**。本当にない場合だけ「特になし」と書く。「全体的に見てほしい」は書かない
6. **本文の主張はすべて diff で確かめる**。やっていない変更を本文が主張するのが、AI 生成の本文で最も多い不整合。テストを足していないなら「テストは足していない」と書き、その理由（何が代わりに保証するか）を子の行に書く
7. **表は列挙できる短い事実だけに使う**（フラグと対象の対応、stacked PR の一覧など）。説明はセルに入れず箇条書きに置く
8. 書式は GitHub Flavored Markdown。バッククォートを含むので、本文は必ずファイルに書き出して `--body-file` で渡す

### 事前チェック（出す前に全項目を確かめる）

1. 検査スクリプトを実行し、表示幅の目安を超える項目を規則 2 に従って見直す（0 件にすることは求めない）

```bash
python3 ~/.claude/skills/pr-body/check.py tmp/pr-body-<番号 or branch>.md --template <テンプレートのパス>
```

2. スクリプトが挙げた「識別子を含む項目」を一つずつ見る。識別子が主語か目的語なら、規則 1 に従って直すか削る。背景で問題の所在を示すための識別子は残してよい
3. スクリプトが挙げた「本文にない見出し」が、削除指示のある節だけであることを確かめる
4. 変更内容の各項目について、根拠になる diff のファイルを挙げられることを確かめる。挙げられない項目は削る
5. 設計の選択とスコープ外の各項目に、理由（「〜ため」）が付いていることを確かめる
6. 素材がなく推測で埋めた箇所が、ラベル付きプレースホルダになっていることを確かめる

## Step 3: 更新時は既存本文と突き合わせる

更新モードでは、書き直す前に既存本文を読み、次のものを**そのまま引き継ぐ**。人が入れた判断や素材は差分から再生成できないため。

- チェックボックスの選択（優先度・確認項目等）
- スクリーンショット・画像・動画
- 背景のリンク（issue・チャット・ドキュメント・エラー監視等）と stacked PR の注記・一覧表
- 末尾の署名行（`🤖 Generated with ...` 等）

書き直すのは、差分とずれた項目と、Step 2 の規則に反する項目だけにする。既存本文にあって新しい本文から消える節・項目は、消した理由とともに最終報告に列挙する（書き直しは静かに情報を落とすため）。

## Step 4: 確認してから反映する

1. 本文を `tmp/pr-body-<番号 or branch>.md` に書き出す（branch の `/` は `-` に置き換える）。pr-create から呼ばれた場合はここで止め、確認と PR 作成は pr-create に任せる
2. 新規なら本文全体を、更新なら旧本文との差分（`diff -u` 相当）をユーザーに見せる。本文のうちユーザーが埋める項目（未チェックのボックス・プレースホルダ）を先頭に列挙する
3. **ユーザーの承認後に**反映する。PR 本文の書き換えは外部への公開なので、承認なしに実行しない

```bash
# 更新
gh pr edit <番号> --repo <owner/name> --body-file tmp/pr-body-<番号>.md
# 新規: 本文ファイルを pr-create または gh pr create --body-file に渡す
```

4. 反映後に `gh pr view <番号> --json body -q .body` で読み戻し、書き出したファイルと一致するか確かめてから完了を報告する
