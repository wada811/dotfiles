# pr-review — 意図ファースト・インラインコメント付きレビュー

「意図を掴む → コードを読む」順番を守り、指摘をGitHubのインラインコメントとして投稿する。意図を先に掴むのは、意図が分からないままコードを読むと、仕様どおりの変更を誤りと指摘したり、意図に反する実装を見逃したりするため。

投稿は取り消せない（コメントを削除しても、通知とメールは相手に届いたまま残る）。そのため、GitHub への投稿はすべて下書きを見せてユーザーの承認を得てから行う（Step 6）。

## 引数

- PR番号（`#42` / `42`）または PR の URL → その PR を対象にする
- `--repo owner/name` → 対象リポジトリを指定する
- 省略 → 下の順で対象を決める

URL（`https://github.com/<owner>/<repo>/pull/<番号>`）が渡された場合は owner / repo / 番号をそこから抽出する。リポジトリの既定をプロジェクトの CLAUDE.md で定めている場合はそれに従う。

省略時は次の順で対象を決める。

1. **会話コンテキスト**: このセッションで直前に扱っていたPRの番号を対象にする（直前に確認・対応していたPR、ユーザーが会話中に挙げた番号など）。レビューを始める前に「コンテキストから #42 を対象にした」と一行で明示し、取り違えていればユーザーがすぐ指摘できるようにする
2. **現在のブランチ**: コンテキストもなければ現在のブランチのPRを探す（`gh pr view --json number,title,url`）
3. **一覧から確認**: それでも特定できなければ、自分にレビュー依頼が来ている open PR を一覧してユーザーに確認する（`gh pr list --search "review-requested:@me" --state open --limit 30`）

---

## Step 1: PR情報の取得

タイトル・本文・head のコミット SHA・base / head ブランチ・変更ファイル一覧・diff を取る。

---

## Step 2: 意図を1文で掴む（コードを読む前に必須）

PR description・リンクIssue・変更ファイルサマリーから
「このPRが達成しようとしていること」を1文で述べる。

**1文で言えない場合** → コードを読まずに、description の追記を求めるコメントを下書きし、Step 6 と同じく承認を得てから投稿して終了する。コメントには、何を・なぜ変えるか（課題と意図）と、やらなかったことと理由の追記を求め、コードを読む前に目的を把握するためだと添える。

本文は `<tmp>/`（プロジェクトの一時ファイル置き場。規約がなければセッションの scratchpad）にファイルとして書き出し、`gh pr review <番号> --comment --body-file <path>` で渡す。`--body "..."` に直接書くと、バッククォートがシェルのコマンド置換として展開されて消える。

---

## Step 3: 4層レビュー（順番を変えない）

差分が依存のバージョン指定だけ（バージョンカタログ・lockfile・ビルドスクリプトのバージョン文字列のみ）の PR は、
4層に当てるコードがない。4層の代わりに下の「Step 3（依存更新のみの PR）」を行う。

**Layer 1: テスト**
- 存在するか（なければ理由を確認）
- ふるまいを表現しているか（実装詳細でなく仕様を）
- エッジケースが含まれているか
- diff に MockK 特有の記法が含まれるか機械的に確認する:
  ```bash
  gh pr diff <番号> | grep -E "every \{|verify \{|coEvery|coVerify|mockk\(|spyk\("
  ```
  1件でもヒットしたら、そのテストコードを評価する**前に必ず** `mockk-testing` skill を
  Skill ツールで読み込む（「該当するなら読み込む」という任意判断にしない）。読み込んでから
  該当箇所の assertion を評価する

**Layer 2: 公開API / インターフェース**
- 型・関数シグネチャが適切か
- 既存の呼び出し元を壊していないか
- 命名が既存パターンと整合しているか

**Layer 3: 実装ロジック**
- 正確性（ロジックが仕様・テストを満たすか）
- エラーハンドリング（握りつぶし・ログ忘れ）
- スレッドセーフ性・リソースリーク

**Layer 4: プロジェクト固有ルール**
- CLAUDE.md の規約に従っているか
- プロジェクトの CLAUDE.md がレビュー用の skill やチェックリストを定めていれば、ここで使う。汎用の観点では、そのプロジェクトで繰り返し指摘されてきた定型の問題を拾えないため

## Step 3（依存更新のみの PR）: リリースノートを自リポジトリのコードに当てる

semver の段位（パッチだから低リスク、等）で判定を済ませない。API 互換のまま挙動だけ変わる変更は
パッチ版にも入る。次の順で進める。

1. **リリースノートの変更点を列挙する**: 旧版から新版までに含まれる全リリース（飛ばした中間版も含む）を
   対象にする。PR 本文に転記されていればそれを使い（Renovate・Dependabot は転記することが多い）、
   なければ公式のリリースノート・CHANGELOG を読む。変更点は1件ずつ書き出し、
   「API 変更 / 挙動変更 / 不具合修正 / 依存の更新」のどれかを添える
2. **各変更点が当たるコードを探す**: 変更点ごとに、該当する API・設定・呼び出しパターンを
   リポジトリ内で検索し、「当たるコードがある（ファイルを列挙）/ ない（検索した語を明記）」を述べる。
   本番コードとテストコードは分けて書く（テストだけが踏む挙動変更もある）
3. **当たるコードを検証するテスト・CI ジョブを名指しし、実行できるものは実行する**:
   作業ツリーを汚さない方法（git worktree 等）で PR の head をチェックアウトして該当テストを実行し、
   結果（実行したテスト・件数・成否）で述べる。推測で「リスク: 低」と書かない。
   実行できない場合は、何が実行できなかったかと、代わりに見た根拠（CI の結果等）を書く

指摘は差分の行に紐付かないことが多いため、Step 5 のサマリー本文に次の表で載せる
（インラインコメントはバージョン指定の行に付けられる指摘だけにする）:

```markdown
| 変更点（版） | 種別 | 当たるコード | 検証（テスト・CI と結果） |
|---|---|---|---|
| <変更の要約>（x.y.z） | 挙動変更 | 本番: なし / テスト: <ファイル> | <テスト名> を実行し green |
```

---

## Step 4: インラインコメントの下書き

指摘をレビュー JSON にまとめる。この段ではまだ投稿しない。

`gh api` の `-f`/`-F` はオブジェクトの配列（`comments[]`）を正しく組み立てられないため、
JSONファイルを `--input` で渡す方式を使う（バッククォート・日本語のシェル展開も回避できる）。

`<tmp>/pr<番号>-review.json` を作る（`commit_id` は head のコミット SHA、`side: "RIGHT"`、`line` は新ファイル側の行番号）:

```json
{
  "commit_id": "<headRefOid>",
  "event": "COMMENT",
  "body": "<Step 5 の形式のサマリー本文>",
  "comments": [
    {
      "path": "<ファイルパス>",
      "line": 35,
      "side": "RIGHT",
      "body": "<コメント本文>"
    }
  ]
}
```

### コメント本文の形式

各インラインコメントは以下の形式で書く：

```
<重大度> **What:** <何が問題か>

**Why:** <なぜ問題か — 根拠・原則・起きうるリスク>

**How:** <修正方向。コード例があれば>
```

What だけでは修正方向が分からず手戻りが増え、How だけでは根拠が伝わらず同じ問題が別の PR で再発する。

重大度ラベル:
- `⛔ blocker` — マージ前必須（クラッシュ・データ破壊・セキュリティ）
- `🔴 major` — 同PR内での修正を推奨
- `🟡 minor` — 次PR可
- `💬 nit` — スタイル・好み（任意）

### 教えるコメント

「このコメントを読んだ人が次に似たコードを書くとき良くなる」コメントを、目安として1件以上含める。設計原則・言語仕様・チームルールの説明を添える。レビューの価値を目の前の修正で終わらせず、次のコードに残すため。

これは目安であり、教える内容がない差分に無理に作らない。依存更新だけの PR には当てない（当たるコードの検証が主で、教える対象のコードがない）。

---

## Step 5: サマリー本文の形式

サマリーは独立して投稿せず、Step 4 の JSON の `body` に入れて、インラインコメントと1回のリクエストで送る。

```markdown
## レビュー: <PRタイトル>

**意図:** <1文>

### 総合判断
<✅ Approve推奨 / 🔄 Request Changes推奨 / 💬 議論推奨>

<判断理由1行>

---
<⛔ N件 / 🔴 N件 / 🟡 N件 / 💬 N件>
各指摘の詳細は上記インラインコメントを参照してください。
```

総合判断の基準：
- **Approve推奨** — ⛔ blockerゼロ・🔴 major 1件以下（次PR合意済み）
- **Request Changes推奨** — ⛔ blocker 1件以上 または 🔴 major 複数
- **議論推奨** — 設計レベルの問題、「15分 sync しましょう」を提案

---

## Step 6: 下書きの確認と投稿

投稿の直前に、サマリー本文とインラインコメント（ファイル:行・本文）の下書きをユーザーに見せ、承認を得る。修正を求められたら JSON を直して再度見せる。承認なしに投稿しない。

承認後に投稿する:

```bash
gh api --method POST /repos/<owner>/<repo>/pulls/<番号>/reviews --input <tmp>/pr<番号>-review.json --jq '{id: .id, state: .state, html_url: .html_url}'
```

投稿したレビューの URL を報告する。
