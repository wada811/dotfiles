# instruction-design — 繰り返し読まれる指示を設計する

指示の価値は、書き手が想定しなかった場面で AI が正しく判断できるかで決まる。想定した場面なら、指示がなくても AI はたいてい正しく動く。だから指示には、想定外の場面に効くもの（目的・理由・判断基準・境界）を厚く書き、想定した場面にしか効かないもの（細かな手順・特定の例）は薄く書く。

対象は、長く使われて周りの指示やコードと食い違っていくもの。一回きりの依頼文は、食い違う前に役目を終えるので対象にしない。

## 観点（厚く書く順）

### 1. 起動条件

指示は読まれて初めて働く。何がきっかけで読まれるかを最初に決める。

- skill の description は全セッションで読み込まれ、呼ぶかどうかの判断にだけ使われる。使う場面・呼び出しの言い回し・隣の skill との境目だけを書き、本文の規則の要約は書かない。要約は毎回の読み込みを重くするだけで、呼ばれる精度を上げない
- 同じ場面で呼ばれうる skill が他にあれば、どちらを使うかの境目を両方の description に書く。片方だけだと、もう片方が呼ばれ続ける
- CLAUDE.md・memory は、置き場所が適用範囲になる。全プロジェクト共通の規則をプロジェクトの CLAUDE.md に書くと、他のプロジェクトで効かない。逆に、固有の規則を共通の場所に書くと、関係ない場面で効いてしまう

### 2. 目的

冒頭の一段落で、この指示が何を実現するか、なぜそれが要るかを書く。規則が当てはまらない場面で AI が立ち返るのは、この段落だけだからだ。

### 3. 判断基準

- **例より基準を書く。** 一つの案件から取った例は、その案件の外では真似できない。例を置くのは、基準を言葉にできないときだけにし、そのときは性質の違う例を複数置く
- **規則は表面の名前でなく、役割や性質に結び付ける。** 特定の見出し名・ファイル名・ツール名に結び付けた規則は、それが違う環境で効かなくなる
- **数値には、厳密な上限か目安かを書く。** 書かないと AI は上限として扱い、数値を守るために他の質を犠牲にする

### 4. 理由

規則ごとに理由を書く。理由があれば、AI は書かれていない場面にも規則を当てられ、当てはまらない場面では外せる。理由がないと、機械的に広げすぎるか無視される。

理由を書けない規則は、根拠を確かめ、なければ削る。「念のため」の規則は、守られるコストだけが残る。

### 5. 境界

- **止まる場所:** 外部への投稿・push・削除など取り消せない操作の前に、誰の確認を得るかを書く
- **任せる先:** 他の指示が持つ手順は、書き写さずに呼び出す。写した手順は、元が更新されても写した側だけが古いまま残る
- **優先順位:** 汎用の指示とプロジェクト固有の指示（CLAUDE.md 等）が食い違うとき、どちらに従うかを書く
- **担わないこと:** 隣の指示と役割が接するなら、何をこの指示が担わないかを書く
- **置き場所:** 公開される場所（公開リポジトリ等）に置く指示には、社内の固有名や URL を書かない

### 6. 検証

- 完了の条件を、観測できる結果で書く（例: 反映後に読み戻して、書き出したものと一致する）。「確かめる」とだけ書くと、確かめた証拠が残らない
- 機械的に判定できることは、スクリプトを同梱して判定させる。AI が毎回手で数える作業は、ずれるうえに遅い
- チェックリストは、規則を問いの形で言い直すだけなら検証として働かない。結果を確かめる項目だけを置く

### 7. 入力と出力

- 入力は、省略されたときに何を対象にするかを書く。同じ種類の指示が複数あるなら、決め方を揃える
- 出力は、成果物の置き場所と、ユーザーに報告する内容を一か所にまとめる。散らばると報告が漏れる
- skill が実行するスクリプトや参照するファイルのパスは、`${CLAUDE_SKILL_DIR}`（skill に同梱したファイル）か `${CLAUDE_PROJECT_DIR}`（プロジェクトのファイル）から書く。Skill ツールは本文の先頭に skill のディレクトリを示すので、`scripts/x.ts` のような相対パスは skill のディレクトリ起点と読み違えられやすく、cwd が別の作業ツリーにあるときも見つからない。マシン固有の絶対パスは、置き場所が変わると壊れる。この二つの変数は Skill ツールで読み込むときにだけ絶対パスへ置き換わるので、SKILL.md を他の指示やスクリプトから直接読ませず、Skill ツールで呼ばせる

### 8. 手順

手順は最小にする。AI は手順の多くを自分で組み立てられ、細かく書いた手順はツールや周りの指示が変わるたびに古くなる。残すのは、順序を間違えると壊れるところだけにする（例: 上書きの前に既存の内容を読む）。AI が自分で組めるコマンド列は書かない。

効いていない指示は削る。読み込みのたびにコストがかかり、効いている指示を薄める。

## 見直すときの進め方

1. **対象と周りを読む。** 対象の全文に加え、対象が呼ぶ指示・対象を呼ぶ指示・役割の近い指示・適用されるプロジェクトの CLAUDE.md を読む。写しの古さや食い違いは、一つのファイルだけを読んでも見えない
2. **観点ごとに所見を出す。** 重い順に並べ、それぞれに直し方の案を付ける。依頼が評価（「どうか」「見直して」）なら、所見を報告して止まる。依頼が修正なら、次へ進む
3. **直す。** 観点 8 に従い、足すより削る方を先に考える
4. **直したことを確かめる。**
   - 名前・見出し・ステージ名を変えたら、他の指示からの参照を検索し、古い参照が残っていないことを確かめる
   - frontmatter が読み込めることを確かめる（skill 一覧に更新後の description が出る等）
   - skill 本文のスクリプト・ファイルの参照を検索し、相対パスやマシン固有の絶対パスが残っていないことを確かめる
   - 同梱したスクリプトは、実際の入力で動かして結果を確かめる
   - 振る舞いまで確かめる必要がある重要な指示は、skill-creator の評価に渡す。読んで直すだけでは、実際にそう動くかは証明できない

## 新しく書くとき

観点 1〜8 の順に中身を決めてから書く。とくに、隣の指示との境目（観点 1・5）を先に決める。後から決めると、既に書いた手順が隣の指示の写しになっていることに気づけない。

文の言い回しの整え方は clear-writing の文の規則に従ってよい。ただし何を書くか・どこに厚く書くかは、この skill の観点を優先する。読み手が人ではなく AI なので、理由・境界・検証の比重が人向けの文章より高い。
